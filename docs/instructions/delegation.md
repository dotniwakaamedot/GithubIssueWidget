## 複数担当と委譲

詳細は [複数担当の手順](../agent-workflow.md) を参照する。

- 複数担当では進行管理、作業、独立した確認レビュー、進行レビューを分け、指示・質問・結果・判断を共有 run の確定ファイルに記録する。所有範囲と担当 ID を明示し、対象ファイルの SHA256 と証跡を確認して対象版ごとに承認する。
- 改善・Skill 提案は採否にかかわらず登録対象とする。登録先への認可を確認し、識別キーで重複照合してから Issue を登録・読戻す。
- 計画の独立レビューを経て、承認された基準コミットから担当ごとのブランチと作業場所を分離する。再開時は旧担当の終了と変更の保護を確認し、基準の取込みが必要なら競合を解消して再検証・再レビューする。基準ブランチ、PR 先と親子 Issue の統合規約は対象の設定で確認する。
- 委譲時はユーザーの原文を一次情報とし、AI の解釈と区別する。重要な要件を省略せず、不明な仕様を推測で確定しない。原文が長い場合は正確なファイルパスを渡し、重要な原文を短い要約で置き換えない。
- 指示には必要に応じて原文、目的、要件、制約、対象外、完了条件、参照ファイル、仮定、未解決の質問を含める。委譲前に要求・制約の欠落、追加した仕様、完了条件の検証可能性、一次情報へのアクセスを確認する。
- `fork_turns` は会話の経緯やニュアンスが重要なら `all`、仕様書と担当範囲が明確なら `none` を使う。`none` では必要な一次情報への参照を必ず含める。
- 子担当は作業前に要求と制約を確認し、矛盾する資料を報告する。担当範囲を超える変更をせず、完了時に要件ごとの対応状況を報告する。
- 親は子の報告だけで判断せず、元の要求、仕様書、変更差分、テスト結果を照合する。報告では実装した要件、変更ファイル、実施したテスト、未検証の要件、仮定、残るリスクを明示する。
