# 作業範囲と検証

## 基本方針

- 要求を満たす必要十分な変更を選び、品質、保守性、安全性を維持しながら作業量を抑える。変更が不要なら、その理由を報告する。
- 既存のコード、設計、ライブラリを活用し、要求に関係しない機能追加やリファクタリングを行わない。
- 調査は要求に直接関係するファイル、シンボル、参照から始め、必要な情報が得られたら広げない。影響範囲を判断できない場合など、必要に応じて調査範囲を広げる。同じ情報の検索や読み直しは、更新確認などの理由がなければ繰り返さない。

## 設計と実装

- 既存のパターンに合わせて変更を局所化し、不要な複雑化、将来の拡張だけを目的とした抽象化、未使用の仕組みや依存関係を追加しない。
- 公開 API やデータ形式の互換性を考慮し、必要なエラー処理を実装する。異常系は現実的な発生可能性と影響に応じて選ぶ。
- ドキュメントは変更の影響を受ける箇所を更新し、不要な設計書やコードの重複説明を作らない。コメントは意図や制約の説明に役立つ場合に記す。

## テストと検証

- 変更の影響とリスクに応じて検証範囲を選ぶ。文言やコメントなどの低リスクな変更は関連箇所の静的確認を基本とし、必要に応じて動作確認やビルドを行う。
- ロジックや機能の変更は、変更箇所に対応する正常系と代表的な異常系を優先し、影響に応じて回帰を確認する。認証、データ、保存形式や基盤処理などは影響範囲を調べ、必要な異常系と回帰を含めて検証する。
- テスト数やカバレッジ自体を目的にせず、無関係なテストを追加・実行しない。必須テストや CI の品質ゲートは省略しない。
- 成功したテストは、対象の変更や新たな懸念などの理由がなければ再実行しない。失敗時は原因と影響を調べ、必要な範囲を修正する。実行できない検証は理由と残るリスクを報告し、未検証を成功扱いにしない。

## 判断と終了

- 新しい本番用依存関係、大規模な設計変更、破壊的な API 変更やデータ移行は、必要性と影響を確認する。ユーザーがすでに依頼・承認した範囲と適用される指示に従い、承認が必要な場合は依存しない準備と検証を進め、具体的な案を示して求める。
- 要求を満たし、必要な検証を完了し、重大な問題や不要な変更がないことを確認したら終了する。必要な確認ができない場合は、未完了事項と理由を報告する。
- 終了条件を満たした後は、改善の余地だけを理由に追加調査、テストや変更を行わない。範囲外の改善案は、ユーザーの判断に役立つ場合に限って報告する。
