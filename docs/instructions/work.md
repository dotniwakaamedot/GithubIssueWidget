## 作業の基本方針

- ユーザー指示、上位指示、認可済み操作と設定を優先する。設定例への記入だけでは外部操作の権限は付与されない。
- 作業開始時に追加指示を確認し、作業内容に関連する場合は [繰り返しの失敗から得た教訓](../recurring-lessons.md) を参照して適用する。他者の作業や未コミット変更を保護する。
- ファイルを参照する前に、作業ディレクトリと対象パスを確認し、存在を確認してから読み取る。存在しない場合は推測したパスを読み続けず、正しい場所を調べる。
### ファイルの確認と変更

- 既存ファイルのパッチは対象ごとに適用直前の内容を読み、文脈文字列・ハッシュ・出現回数と複数箇所の順序を照合する。独立したファイルや離れた箇所の更新は可能な範囲で分割し、結果を読み戻す。拒否時や並行編集後は現行版を再確認し、経過保存時も確認を省かず、ユーザーの停止条件を優先する。
### 出力とログ

- 出力を取得する前に必要な対象・件数・行の長さを見積もり、検索範囲や取得項目を絞る。既知の短い出力は対象選択と上限設定を同じ操作で行い、大きさが不明な場合は範囲を絞るか分割する。複数の結果、長い行、検索コンテキスト、見出しやエラーを含む合計に余裕を持たせ、内側と外側の出力上限がある場合は両方を考慮する。
- ツール探索はまず名前を絞り、必要な定義だけ表示する。長い行を含み得る検索では行番号や行長を先に確認し、必要な文脈を分割して取得する。行数の制限だけで出力量が収まるとはみなさない。
- スクリプトで環境固有の API を使用する前に、実行環境と必要なメソッドの存在を確認する。
- 出力量が不明な資料は原則として一度に１文書の必要な短い範囲を表示する。複数結果を表示する場合は各結果と包装の最大長を合算し、内外の上限に余裕を設ける。分割した場合も必要な文脈と終了結果を確認する。
### 外部一覧の集計

- 外部一覧の集計前に、合成データで JSON の型・配列の階層・要素数とページ結合を検証する。実際の集計では終了結果、ページ取得完了と件数を区別し、取得失敗や空結果を不存在の証拠としない。失敗時は秘密・応答本文・例外全文を出さず、取得可能なエラー種別・HTTP 状態・終了コード等の安全な診断情報を区別して記録する。
- ページ付き一覧の全件確認では API の終端条件と継続情報を応答から確認し、継続先の対象・形式・順序を検証する。短いページだけを終端の証拠とせず、不正・循環・上限・途中失敗は未完了とする。短いページに次ページがある例、正常終端、途中失敗、不正・循環を合成試験し、同時更新による制約を記録する。
### 大量出力と失敗時の扱い

- ビルド・テストなど大量の出力が予想される操作では、機密情報の扱いを確認した上で可能なら最初から適切なログへ保存し、元の処理の終了コードと必要な範囲を別に確認する。トークンや非公開情報を含む可能性がある場合は、そのまま保存せず、安全な項目の抽出、保存しない方法、または適用指示に沿う保護済み保存先を選ぶ。保存先、アクセス権、保持期間と上書き・削除の扱いは適用指示に従う。
- 出力が切り詰められた場合は欠落部分を未確認として扱い、元の処理の終了コードや完全なログを別に確認できる場合はその証拠と区別する。失敗記録・独立分析とユーザー指定の停止条件に従い、再取得が許される場合は既存の完全なログを優先し、なければ安全に再取得できる出力を適切なファイルに保存して、必要箇所を分割して読む。すでに失われた出力は復元できるとみなさず、外部操作や書込みを伴う処理を出力確認のためだけに再実行しない。切り詰め・省略された表示や要約を完全な証拠としない。
- 同種失敗の停止条件がユーザーに指定された場合は、累計の教訓集計と分け、指定された一度の指示と処理の間の回数で判断する。独立した作業の継続も、ユーザーの停止指示と適用される手順の範囲内で行う。
### 制約付き試験と監督プロセス

- プロセス数や子生成の制約を伴う試験では、制約前に実行ファイルの実体、起動ラッパー、想定する子プロセスと期待結果を確認し記録する。制約下の合成試験と実際の対象プログラムの検証を区別し、実行経路の変更だけで終了保証や安全性が確認できたとはみなさない。
- 外部書込みや秘密を扱う監督プロセスは、予約・子生成・識別・登録・再開・送信・読戻し・終了確認を順序付け、各境界の失敗・監督者停止・不明時の禁止事項と復旧証拠を表にする。認証・出力上限・秘密の非出力・成功条件・親子孫の終了根拠も定義し、実装と合成障害試験を独立確認する。不明な場合は実書込みを無効にし、実 OS 障害や外部処理の無条件の停止保証を主張しない。
### 調査と失敗の記録

- 調査・検証の結果、確認された事実、推測、未確認事項を区別する。未完了事項と具体的な次の作業を報告する。
- 不具合では対象版と期待動作を確認し、再現・ログ・コードを根拠に原因を切り分ける。元の事象と回帰を確認し、因果関係が未確認なら解決済みと断定しない。
- [失敗記録](../failure-log.md) は毎回読む必要はなく、失敗を認識したときに手順と該当する分冊を確認し、自動的に記録・集計する。同じ失敗が累計3回以上になったら、複数エージェントで対応を検討し、結果をルールに反映する。利用できない場合は未完了として記録し、再開条件とともに報告する。失敗があった作業の終了時は記録漏れと教訓への反映を確認し、具体的な教訓を番号付きで報告する。なければその旨を伝える。記録できなかった場合は理由と未記録の内容を報告する。
