## 確認結果

- 現行 `list_issues` は `fetch_pages_checked` の結果を `finish_board` に渡す。`finish_board` は `ConnectionLock` と設定ファイルのロックを取得し、リカバリー・設定・資格情報の再読込み後に `validate_board_snapshot` を呼ぶ。現行ファイルでこの構造を静的に確認した。
- `TEST_AFTER_HEADERS` は `cfg(all(test, windows))` に限定され、`fetch_pages` の `get_api_response(...).await` が戻った後、本文デコードより前に一度だけ取り出される。現行 `get_api_response` の共有ファイルロックはその関数内のガードであり、成功して戻った後のフック時点には保持されない構造。エラー応答・実行時の同期結果は未検証。
- 計画は旧方式を置換し、親の `APPDATA` を変えず、隔離領域の明示パスを `process_lock_at` / `write_settings_at` に渡す。子の製品 `settings_path` との一致、子から見た別プロセス更新、正常系後に競合系のみで一度限りのフックを設定する順序を明記した。合成 ID と作成段階は書込み前に flush し、生成値と一致する資格情報だけを削除する。
- 親の依頼・計画には、前基準 `00A8A973753DBD1A90E9337C5724247ABC6A10CDA871D87881DC27FE3B2BFCEF` からの `finish_board` 分離と test-only フック追加を親が所有すると記載されている。現在の該当構造と整合する。
