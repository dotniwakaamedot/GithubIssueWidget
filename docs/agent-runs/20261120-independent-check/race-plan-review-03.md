## Blocking 指摘

### B-01: 親が使用する設定・ロックのパスを固定する必要がある

現在の製品関数 `process_lock()` と `write_settings()` は呼出しプロセスの `APPDATA` を参照する。末尾案では親テストの環境を変えず親がロック・設定更新を行うため、これらをそのまま親から使うとユーザー側の設定領域を参照・更新する可能性がある。現行コードには明示パスを受ける `process_lock_at` と `write_settings_at` がある。

**対応案:** 親は、子の `APPDATA` から解決される隔離用 `github-task-widget/settings.lock`・`settings.json` と同一の絶対パスを明示し、`process_lock_at` / `write_settings_at` を使用する。実体と一時領域内であることを確認し、不一致なら書込み前に停止する。子では製品関数がその同じパスを解決することを検証する。設定更新が本番の `save_connection` 全体を通らないことも結果に明示する。

## Non-blocking 確認事項

1. 旧段落には孫による更新が残り、末尾は親による更新としている。末尾が旧方式を置き換えることを明記し、空領域の確認、初期設定、正常系、競合系の順序と一度限りのフックが競合系だけで作動する条件を固定する。
2. ローカル通信先・proxy 無効化、子の非表示と PID、タイムアウト、エラー・panic 時の cleanup を実装後に確認する。強制終了時も追跡できるよう、合成 ID と作成段階は資格情報を書き込む前に記録・flush し、値自体はログへ出さない。
3. 本テストは実 WebView・実 GitHub・設定画面からの実更新を通さない。成功しても UI 統合や最終照合後の別プロセス変更を証明したことにはしない。
