## B-01 の再確認

### 確認できた改善

- `list_issues` は `fetch_pages_checked` を経由し、ページ取得後に設定・資格情報を読み直すクロージャーを実行してから結果を返す。クロージャーは `validate_board_snapshot` で接続先、資格情報 ID、トークン値を照合し、不一致時に Issue を返さない。
- `in_flight_board_is_not_returned_after_credential_change` はローカル HTTP サーバーで要求受信後の応答を待機させ、その間に別スレッドが合成ストアの資格情報を変更してから応答を返す。テストは `fetch_pages_checked` と `validate_board_snapshot` を通り、合成トークン・Issue タイトルを含まないエラーを確認する。以前の「取得完了後に直接検証するだけ」のテストより、取得処理と変更順序の証拠が強い。
- `%TEMP%/githubissuewidget-inflight-tests-20261120.log` には当該テスト `ok` と `48 passed / 4 ignored` がある。ログ SHA256 `8A3EB3ED0B6336CB8F560BE174AF154DA2740B857AF64CA9949CA807EBC13082`。ログの更新時刻は対象ソースの更新時刻より後だが、ログ自体にはソース SHA が埋め込まれていない。この担当はテストを再実行していない。

### 残る blocking: テストと実際のロック・読戻し経路が異なる

- テストの現在状態は `Arc<Mutex<(Settings, Option<String>)>>` にあり、検証クロージャーもテストが別に用意する。一方、製品側クロージャーは `ConnectionLock`、`process_lock`、`recover_pending`、`read_settings`、`read_token` を使う。テストは実際の `list_issues`、Windows Credential Manager、React への応答配送を通らないため、製品側クロージャーの接続やストア読戻しの失敗・並行挙動を単独では証明しない。
- さらにテストの `RateCooldown::default()` は共有状態を使わない `false` だが、製品は `RateCooldown(AtomicU64::new(0), true)` を使用する。製品の `get_api_response` は `send().await` を含む間 `process_lock` を保持するが、テストサーバーは応答ヘッダーを送る前に合成ストアを変更する。そのため、テストの停止位置で別プロセスの実際の設定変更が成功する状況を再現してはいない。製品ではヘッダー受信後の本文取得中やページ間など別のタイミングもあり得るが、今回その競合は未実行。
- 対応案: 隔離 APPDATA と合成資格情報を使い、実際の共有ロックと製品の読戻しクロージャーを通るテストを追加する。HTTP ヘッダーと本文の送信を分離する、またはページ間を同期して、製品のロックが解放された後に別操作で設定・資格情報を変更し、呼出し元に旧 Issue が返らないことを確認する。フロントエンドの旧応答抑止は既存のモックテストに加え、可能な範囲で実経路との結合を確認する。実資格情報や実 GitHub 書込みは不要。
