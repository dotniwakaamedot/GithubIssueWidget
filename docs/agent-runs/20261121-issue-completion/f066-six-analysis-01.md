# F-066 発生6の独立分析

担当 `/root/failure_review`。計画・レビュー・失敗記録と既存ルールの読取りによる分析であり、計画の承認ではない。アプリ起動、合成障害試験、外部通信、API 動作の実測は行っていない。

## 確認された事実と原因の確度

- `gui-supervisor-plan-01.md` は Job を作り、子を suspended で生成して Job 割当後に再開する案で、生成・割当・再開が失敗した場合「対象を再開しない」としている。停止側は Job 内の終了と active count を根拠とするが、Job 割当前の直接子に対する終了・復旧は指定していない。
- `gui-supervisor-plan-review-01.md` は、割当失敗時に Job 外の停止中の子が残り得ること、生成直後から割当前の監督者停止時は kill-on-close がその子を保護できないことを指摘した。これは計画の境界条件の欠落であり、実プロセスの残存や OS 障害は観測されていない。Win32 API、親 Job や sandbox の制約・挙動は本分析で実測していない。
- 直接の原因は、Job の所属が成立する時点と、それ以前に存在し得る直接子の所有・異常終了・復旧を計画が結び付けなかったことである。なぜ既存ルールが計画へ具体化されなかったかは証拠がなく未特定。今回を F-066 の１件とする分類は失敗記録に基づく。

## 既存ルールとの照合と具体的適用

`docs/instructions/work.md` は予約・子生成・識別・登録・再開・終了確認を順序付け、各境界の監督者停止と不明時の禁止事項・復旧証拠を定義するよう求める。`docs/recurring-lessons.md` の F-066 も親子孫の終了根拠と合成障害試験を要求する。したがって一般ルールの新設より、今回の境界に既存ルールを具体化する。

1. 生成前、生成成功直後・Job 割当前、割当失敗、割当後・再開前、再開結果不明、実行中、停止・照会失敗を分け、各状態で識別可能なハンドル・情報、終了要求の対象、期限、終了根拠、復旧責任者と後続起動の禁止条件を記す。Job 外の子に kill-on-close や active count を適用したとみなさない。
2. 直接子の生成と Job 所属を原子的にできる仕組みが、対象 Windows・親 Job・起動経路で利用可能かを確認し、必要な失敗境界を検証する。利用できない場合は、生成直後の監督者停止を含めた独立監督・識別・復旧の成立を具体化する。どちらも成立を証明できなければ、状態を不明として実アプリ起動を禁止する。PID 単独や対象名だけで他プロセスを終了しない。
3. 子の状態照会や終了要求・確認が失敗する場合、残存可能性を記録して後続起動を止める。監督者停止を含む各境界を、実アプリを無効にした合成障害試験で検証し、対象版を独立レビューする。Job の count 0、親終了、EOF のいずれか単独を未所属・breakaway を含む全子孫終了の証拠にしない。

再発防止のため既存 F-066 教訓に発生6と上記の所属成立前の境界を追記し、読み戻すことを推奨する。新たな一般ルール・Skill の提案はない。各 API の成否、原子性、設計の成立、実環境の終了、再発防止効果は未確認であり、OS 障害時の無条件の終了保証は主張しない。ユーザー指定の２回連続の同種失敗による停止を優先する。
