# GUI 診断スクリプトの独立レビュー

判定: **要修正**。対象版のまま実アプリ起動の安全性を承認できない。コードと既存記録の読取りであり、合成試験やアプリ起動は実施していない。

## 指摘

1. **標準エラー由来の数値が許可リストなしに出力される。** `gui_diagnostic.py` の `diagnose` は `gui_probe.classify` の結果をそのまま使い、`os error (\d{1,5})` に一致した任意の１数値を `os_error` に出す。例えば合成文字列 `os error 12345` の数値はそのまま表示される。固定分類のみという依頼に反する。未認識を固定値 `unknown` にし、必要な数値のみ列挙したうえ、秘密らしい数値・境界・複数一致・上限超過を含む合成試験で出力全体を検査する。
2. **fixture の実体と権限が検証されない。** 引数は空の既存ディレクトリかどうかしか判定せず、指定範囲、再解析ポイント・リンク、親のアクセス権、実行直前の内容や置換を確認しない。`APPDATA` と `LOCALAPPDATA` を置き換えても Windows Credential Manager は隔離されない。`main.tsx` は起動時に `connection_info` と `pending_creation` を呼び、`main.rs` の復旧処理は条件によって資格情報削除を行う。安全な空の専用実体とアクセスを事前に確認し、起動中も他者が設定を書き込めない前提を明示する必要がある。OS 資格情報全体が隔離されるという保証はない。
3. **例外出力と処理終了が未制御。** ディレクトリ検査や `Popen` 等の予期せぬ例外は既定の traceback によりパスや OS 由来の自由文を表示し得る。捕捉方法自体の失敗も固定カテゴリに落とし、元データと例外全文を表示しない設計と合成試験が必要。また 8 秒経過後に `process.wait()` が期限なしで待ち続け、正常なウィンドウ表示、停止指示、子孫・パイプの終了は確認しない。監督側の中断時も含め観測と終了確認を定義し、終了不能は不明と報告する必要がある。タイムアウト時の合成試験は直接の子を明示終了するのみで、実際のコード経路や子孫の終了を検証していない。

## その他の検証範囲

`HRESULTS` と `CRATES` は列挙した固定文字列のみを返すが、単なる出現を原因やソース位置の証拠にはできない。現在の合成試験は未知値と境界の一部を扱うが、例外、数値漏出、配置されたリンク、変更競合、監督停止を扱わない。`overflow` は示されるが、分類が先頭 32768 バイトに限られることに注意する。stderr 本文が失われた前回の原因を復元するものではない。
