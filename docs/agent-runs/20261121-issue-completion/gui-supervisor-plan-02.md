# GUI 単発診断の監督方式案 第2版

第1版 `gui-supervisor-plan-01.md` と `gui-supervisor-plan-review-01.md` を引き継ぐ。目的・fixture・秘密非出力・観測・停止・合成試験・対象版レビューの条件は第1版のとおり。次の点を置換・追加し、証拠のない保証を行わない。

## 生成と復旧

Windows 10 以降の `PROC_THREAD_ATTRIBUTE_JOB_LIST` を `STARTUPINFOEXW` と `CreateProcessW` に設定し、作成時に専用 Job を指定する。`lpApplicationName` は対象 EXE の絶対パスを指定する。Microsoft の [UpdateProcThreadAttribute](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-updateprocthreadattribute) は子に割り当てる Job ハンドルのリストと対応 OS を規定するが、生成 API の途中で監督者が終了した場合の全状態を本計画は保証しない。対応機能・親 Job・同一セッション・権限を実環境と合成試験で確認し、使えない場合は実アプリを起動しない。属性値とハンドルは必要な期間保持し、子に Job ハンドルを継承させない。

実行前に一意の識別子と EXE ハッシュ・fixture・計画対象を予約記録へ安全に保存する。子の引数にも一意識別子を指定し、CreateProcess の戻り後はプロセスハンドル、PID、作成時刻、実行パス、Job 所属を確認して結果を記録する。生成途中に監督者が落ちた場合は状態不明とし、Job kill-on-close の結果を推測せず予約を保持、同じ対象の再起動を禁止する。再開時は同一セッションで実行パス・作成時刻・一意引数を独立照合して候補を確認する。識別または終了の確認が不完全なら候補に終了操作を行わず不明のままとし、手動復旧まで後続を禁止する。引数の一意性だけで PID 再利用を否定しない。

生成 API が明示的に失敗した場合でも生成途中の状態を不明として予約を保持し、プロセス不在・終了を独立確認するまで後続を禁止する。成功後の再開・照会失敗では、保持する Job と直接子のハンドルを使い `TerminateJobObject`、必要なら特定された直接子への終了要求を行い、各戻り値・期限付き待機・Job active count と捕捉スレッドの終端を別々に確認する。不明の場合は復旧証拠を保持する。Job の count 0 は breakaway や未追跡プロセスの不存在の証拠ではない。

## 実行前の検証追加

- 生成前、生成 API 中、生成後の観測前、停止時に監督者を止める合成試験を行い、予約と子の識別・復旧の可否を記録する。状態不明のとき再起動が禁止されることを検証し、OS 障害の一般的保証には拡張しない。
- 生成・所属確認・再開・終了・照会・待機・パイプ回収の各異常を注入し、戻り値と期限、出力全体の固定分類、残存不明の扱いを検証する。Job 属性未対応や親 Job 制約でも fail closed とする。
- ウィンドウは保持ハンドルに対応する PID と作成時刻を照合し、見つからない・不可視・照会失敗を区別する。fixture への別プロセスによる競合防止を確認できなければ実行しない。

第2版は方式案であり、API の実装可能性・合成試験・独立レビュー・実アプリの安全性は未確認。
