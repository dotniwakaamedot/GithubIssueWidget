# GUI 監督方式案の独立レビュー

判定: **要修正**。捕捉、fixture、実行前ゲートの方向は既存の指摘を扱うが、子の生成から Job 割当てまでの失敗・監督者停止時に、対象を残さず状態を確認する設計が不足する。実アプリ起動の承認ではない。

## 指摘

1. `CREATE_SUSPENDED` の成功後、Job 割当てが失敗した場合、その子は Job の外にいる。「対象を再開しない」だけでは停止した子が残り、Job の kill-on-close では終了しない。保持するプロセスハンドルで当該子を終了し、期限付きで終了を確認すること。確認できない場合は残存可能性と対象識別情報を保護し、後続起動を禁止する。再開失敗の場合も、再開が実際に失敗したと確認できるかに応じて Job と直接の子の終了・照会を明記する。
2. 生成後・Job 割当て前に監督者が異常終了すると、未所属の suspended 子には Job の kill-on-close が及ばない。この境界について、生成時の原子的な Job 所属が実行環境で利用可能か確認する、または別の監督者による識別と復旧を具体化する必要がある。いずれも実証できなければ残存を不明として後続実行を禁止し、無条件の終了保証を主張しない。合成試験ではこの境界で監督者を停止し、子の状態と復旧を確認する。

## 追加で明確にする事項

- 終了要求の具体手段、要求不能・Job 終了失敗・直接子の待機失敗・active count 照会失敗・パイプ回収期限超過を区別する。Job 外への breakaway や未追跡プロセスについて count 0 を全子孫終了の証拠にしない。
- ウィンドウは対象の実行ハンドルに対応する PID と照合し、取得失敗・不可視・存在なしを区別する。PID の再利用や別のウィンドウを成功の根拠にしない。
- fixture の同一ユーザー競合を防げない場合は不明として起動しない、というゲートを維持する。空の状態確認後から復旧処理までの競合は ACL だけで解消したとみなさない。
- 許可 enum のみの出力を、失敗や捕捉スレッド例外を含め実際の監督プロセスの出力全体で試験する。上限超過時の不一致を不存在と扱わない。Windows API の数値と例外文字列はそのまま出力しない。
