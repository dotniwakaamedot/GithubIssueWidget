# GUI 起動失敗の切り分け案

担当 `/root/failure_review`。資料とコードの読取りによる提案であり、GUI 起動・外部通信・実験・権限変更は行っていない。どの方式も実環境での安全性や成功を保証しない。

## 結論

まず追加起動なしに既存証拠と Windows の実行環境を調べ、その結果で診断対象を絞る。実アプリを再起動する場合は、旧診断スクリプトをそのまま使わず、出力先・隔離先・終了観測を明示した単発の限定検証を用意する。動作中 GUI を待つために無期限待機や、証拠のない子孫の強制終了を行わない。以前のエラー本文は失われており、調査しても復元できるとは限らない。

## 根拠

- `handoff-gui-stop-02.md` は同じリリース EXE の終了コード101と、標準エラー内の `panic`・`WebView2` の固定分類を記録している。本文と発生箇所はなく、WebView2 ランタイムや製品の欠陥を確定できない。
- `verification-20261120.md` の設定画面表示や、独立 APPDATA・LOCALAPPDATA の生存確認は別ハッシュの過去版の結果。実環境で表示可能だった履歴として参考になるが、現行 EXE の成功や同じ環境条件を証明しない。
- `main.tsx` は起動時に `connection_info` と `pending_creation` を呼ぶ。`main.rs` は前者でロックと復旧処理を実行する。復旧記録がなければ資格情報を削除せず、設定がなく ID が空なら `read_token` は資格情報ストアを呼ばない。一方、ロック用ディレクトリ・ファイルは作り得る。`creation.rs` の起動時の pending 読取りはロックを取得する。空の設定先という事前条件と、その維持が崩れればこれらの推論は使えない。APPDATA の変更は Windows Credential Manager 自体の隔離ではない。
- `gui-diagnostic-review-01.md` は現行診断版の任意数値・例外文の出力可能性、fixture の確認不足と無期限待機を指摘する。前回の合成試験が成功していてもこれらを覆さない。

## 起動前にできる調査

対象 EXE とソースの SHA、ビルド記録、実行ユーザー／対話セッションの種類、WebView2 Runtime の登録と利用可能なバージョン、既存 fixture の属性・アクセス可否を読み取りで確認する。レジストリやファイルは根拠のある親から列挙・存在確認し、空とアクセス失敗を区別する。イベントログは、対象時間と既知のプロバイダーでメタデータ・件数だけを絞り、本文・ユーザー名・パス等は画面や未保護ファイルに出さない。対応イベントがない場合、正常や原因不存在の証拠にはならない。以前の記録と現環境の違いを比較し、差がなければ不明とする。これらは再起動を伴わないが、原因が分かる保証はない。

## 単発検証の候補と境界

簡潔な観測だけなら、専用の空設定・WebView2 データ先を用いた通常の EXE 起動と Windows のウィンドウ・プロセス観測を使い、アプリの stdout/stderr を破棄する方法がある。これは画面表示・存続と終了状態を確認する方法であり、今回必要な panic の詳細は得られない。実行するなら既存 fixture や実設定を流用せず、以下の条件を満たすことが前提となる。起動が再び失敗したとき、情報が得られないまま同じ操作を反復しない。

詳細が必要なら、別途監督方式を設計し、固定カテゴリに限定する捕捉版を合成障害試験と独立レビューに通す。未知の OS 数値・自由文・例外は出さず、既知値の出現も原因と同一視しない。生の stderr を非保護ログに書かない。旧 `gui_diagnostic.py` と `gui_probe.py` の実アプリへの使用はレビュー指摘が解消されるまで避ける。診断だけが目的なら実 PAT や実 GitHub 操作を一切含めない。

| 境界 | 必要な確認・記録 | 失敗・不明時 |
| --- | --- | --- |
| 実行前 | 対象 EXE のハッシュ、実行ユーザー・対話セッション、単発であることを記録。新規専用ディレクトリを指定領域内に作り、親からの再解析ポイント・実体・アクセス権と空であることを確認。APPDATA と LOCALAPPDATA は別の空領域とし、起動中に別プロセスが変更しない前提を確保する。 | 範囲、アクセス、競合、設定・復旧記録の不存在が不明なら起動しない。ACL だけでは同じユーザー内の競合を防げるとは限らず、その限界を記録する。 |
| 起動・観測 | 予め確認した実行ファイルを一度だけ起動し、直接の子のハンドル・作成時刻・実行パスで同一性を確認。一定時間内の窓の存在とプロセス生存・終了コードを区別し、入力・設定・資格情報操作・GitHub 書込みはしない。 | プロセス生成・同一性・窓確認が不明なら成功扱いしない。タイムアウトは単なる観測結果であり、終了したとは扱わない。 |
| 終了 | 対象ウィンドウに通常の閉じる操作を送り、保有ハンドルで直接の子の終了を期限付き確認する。子孫がある場合は専用の実行前設計に基づき識別・終了確認を別々に行う。 | 終了・子孫の同一性が不明なら無関係なプロセスを終了せず、残存・fixture を保護し、確認できた範囲と復旧手順を記録する。単独の親終了・パイプ EOF は子孫終了の証明ではない。 |
| 捕捉方式を使う場合 | stdout/stderr を並行して上限付きで回収し、固定 enum のみ出す。例外・上限超過を固定分類し、通常、異常、秘密風入力、未知値、子孫のパイプ保持、監督者停止、終了・照会失敗を合成試験する。 | 捕捉、期限、子孫、出力抑止の保証に欠落がある場合は実アプリで使わない。OS 障害・breakaway に対する無条件の終了保証はしない。 |

Windows Job Object を使用する場合も、子を実行前に Job へ割り当てる順序、失敗時の扱い、子孫の breakaway、監督者停止や API 失敗の観測を別途実装・検証しなければ保証にならない。既存の実 GitHub 用ハーネスについて、今回の GUI に転用可能とする根拠は確認していない。
