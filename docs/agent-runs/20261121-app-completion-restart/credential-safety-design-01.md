# Windows 合成資格情報試験の安全設計 01

## 結論

既存 ignored test をそのまま実行せず、**実書込み前に一意な合成 service 名と復旧情報を耐久記録する専用の試験経路**を、別依頼・独立レビュー・合成故障試験を経て用意することを提案する。本設計は読取り調査のみであり、実装や実 OS 試験は未実施。実 PAT、実アプリの service と設定は対象外で、アプリ完成を証明しない。

事前の不存在確認だけでは第三者による同名作成との競合を原子的に防げない。利用する API に create-if-absent がない場合、試験専用 Windows ユーザーなど他者の書込みがない隔離環境を検証の前提とし、前提が成立しなければ書込みを禁止する。UUID と事前確認だけを所有権の証拠にしない。OS 異常や停止後の即時停止・復旧は保証しない。

## 提案する実行順序とゲート

1. 独立した後続担当が、製品と別の専用試験領域に最小実行プログラムと監督・回復手順を作る。依存・入力・実行ファイル・プログラムの SHA、予定する親子プロセス、ログ先、合成値のみを使うことを事前に固定し、製品や既存の ignored test は変更しない。提案時点で実装の所有者・ファイル名・成果物版を管理が依頼で明示する。実 OS 操作なしのモックを先に実行し、別担当がコードと障害試験結果を承認する。
2. 単一の専用試験ランを排他ロックし、十分なランダム UUID を含む `github-task-widget-test-<UUID>` と `synthetic` を決定する。記録先を専用 run 内に排他的作成し、試験 ID、service、user、対象 Windows ユーザーを識別する情報、実行体 SHA、段階、時刻、実行モードを保存し flush してから読み戻す。記録・権限設定・読戻しに失敗したら実書込みを禁止する。記録に PAT、credential の値、例外本文は保存しない。名前は秘密ではないがログのアクセス範囲を制限する。
3. 専用 service の完全一致名だけを問い合わせ、明確な NoEntry のみを不存在とする。API エラー・アクセス拒否・状態不明は不存在にしない。隔離 Windows ユーザーと当該名前空間の排他性を確認する。競合排除を立証できない場合は停止する。`github-task-widget` および登録外の service は読取・削除しない。
4. 書込み前段階を耐久記録する。監督プログラムと OS API 呼出し実行体を明確に分離する場合は、子の識別・終了監督・登録と開始の順序を実装・検証し、登録不能や監督者停止時に新たな書込みを始めない。簡潔な案は、事前登録済みの単一実行体が当該 service のみを操作し、親が実ハンドルで終了を監督する構成である。ビルドやテスト起動器の子孫は実書込み開始前に終了させ、実行体が生成する子・スレッドの有無はコードと試験で確認する。PID のみを所有権・終了の証拠にせず、生成時刻・実行体 SHA とハンドルを照合する。
5. 所有する合成 entry のみで、固定された合成値 A を保存、読取・比較、合成値 B に更新、読取・比較、削除、NoEntry を確認する。値は実行中の比較だけに使い、ログ・結果・画面に出さない。各段階の前後を durable journal に記録し、エラー分類・終了コードと操作の成否だけを残す。途中で結果不明となったら次の変更や盲目的な再送を止める。
6. 実行体の終了をハンドルと終了コードで確認した後、別の読取で登録済み完全一致対象の NoEntry を確認し、最終結果と記録の整合を監督者が保存する。残留や状態不明なら未完了。正常終了のみでは削除済みとみなさない。cleanup は既存エントリ保護と所有権を確認できる場合のみ合成対象に限定し、再開の判断・証拠を別記録に残す。

## 境界ごとの異常時

| 境界 | 失敗・不明時の禁止と再開条件 |
| --- | --- |
| 排他予約・記録・flush・読戻し | 書込みを開始しない。実体・権限・識別子を再確認し、新規の依頼で再開する。 |
| 不存在確認・隔離 | エラーや衝突は不明／衝突として停止。別 ID を無条件再生成・再送せず、前の記録と実状態を確認する。別プロセス競合を排除できなければ実行しない。 |
| 実行体の識別・登録・起動 | 記録と一致しない実行体、登録不能、親と子の状態不明では書込みを禁止。起動済みならハンドル・生成時刻等で識別し、終了を確認するまで再開・削除しない。 |
| 保存・更新・読取 | 各段階が不明なら新たな保存・更新をしない。監督対象の終了と登録済み完全一致名を確認し、事前記録・所有権・隔離を照合してから専用復旧手順を判断する。 |
| 削除・後読取 | 削除の応答不明を成功と扱わず、実行体と子孫終了後、完全一致対象の読取で状態を確認。読取不能や対象が想定外の場合は停止し、他の service は触れない。 |
| 監督者停止・タイムアウト | 実行体が生きている可能性を前提に再開や cleanup を禁止。ハンドルを失った場合は実行体・生成時刻・監督記録の照合で停止を確認し、不明なら保留。PID 再利用に注意。OS 停止・ハング下の確実な終了は主張しない。 |
| 値・ログ・権限 | 合成値以外を入力しない。秘密や非公開情報が混入し得る生出力・例外本文は保存しない。出力制限・保存先 ACL・保持期間と削除可否を事前確認し、不能なら実行しない。 |

## 事前試験と独立確認

モック API と一時領域で、正常保存→更新→削除、初回読取 NoEntry 以外、同名衝突、journal の create/flush/readback 失敗、登録前後・書込み直前直後・更新中・削除中の中断、応答消失、削除後読取失敗、監督者・子停止、タイムアウト、PID 不一致、cleanup の対象不一致をそれぞれ注入する。各ケースで「追加書込みなし」「登録外 service にアクセスなし」「不明を成功にしない」「記録から対象と状態を識別できる」を検証する。機密ダミー値がログに現れないことも確認し、失敗時の実行結果とログは安全な範囲だけ保存する。プロセス制御の試験は実行体・ラッパーと子孫を分けて監督し、合成故障が実 OS 障害の停止を保証するとは扱わない。

独立レビューではコード・指定 SHA・実行体・権限・対象範囲・障害表と観測ログ、親子孫の終了証拠、再開手順を照合する。実 OS 合成テスト成功後も、実アプリの Credential Manager 操作、PAT の保存・更新・削除・再起動後復元、実 IPC の秘密非露出を別検証する。実験に使った専用 service の残留を確かめるまで完了としない。
