- 担当 `/root/assignment_failure`。元操作の再表示・再実行をせず、担当者の記録と回答を照合した。製品・共有記録は変更していない。
- 結論: 出力切り詰め２件はいずれも取得前に実際の出力量を見積もらなかったことが確認された。コネクタ引数誤りは型定義を確認せず推測したことが確認された。再発防止の効果は未検証。

## 事実と分析

1. `/root/failure_review`: ２文書に広い語６件を検索し、事前の定量的見積りなし。内側上限 4,500 に元出力 12,790 tokens、終了コード 0、完全ログなし。多くの一致行は確認されたが、失われた行と語ごとの寄与は不明。元操作を再実行せず既知行の短い範囲へ変更し、その後の限定取得では切り詰めなし。根拠 `failure-review-question-01.md`、`failure-review-answer-01.md`。
2. `/root/issue_completion_audit`: `search_issues` ２件の `structuredContent` 全体を同時出力。本文を含む全長を見積もらず、検索結果数上限 30 を出力量上限と誤認。元 13,358 tokens、内外は既定上限、外側 exec 完了。各検索の `isError`、完全結果、欠落は不明で完全ログもない。根拠 `tasks/01/result-03.md`、`questions/01-question-03.md`。
3. 同担当の `fetch_issue_comments` 初回は、名前と概要のみ確認し型定義を見ずに `repository_full_name` と推測。必須 `repo_full_name` 不足で `INVALID_ARGUMENT`、正しい引数で後続取得に成功。秘密や外部書込みは対象記録に現れない。根拠同上。

## 適用と提案

- `docs/instructions/work.md` は対象・件数・行長の事前見積り、長さ不明時の分割、複数結果と内外上限の合算、切り詰め箇所を未確認とすることを要求する。件数制限だけでは本文を含む出力の長さを保証できない。既存ルールを適用し、検索対象と必要フィールドを先に限定し、長い行を含む場合は行長も確認する。結果の完全性・終了を別々に確認する。
- コネクタは呼出前に必要なツールの型定義・必須引数を確認し、引数を推測しない。エラー後の再取得は副作用のない操作に限定し、成功と失敗を区別する。
- `docs/failure-log-001.md` の F-001 発生60・61と別件の暫定記録は対象の３事象に対応する。累計の欠番・重複および引数誤りの同種累計は未照合。上記策は既存指示の具体的適用であり、効果は未検証。記録の更新・集計は管理担当に引き継ぐ。
