## 実 OS 試験に対する blocking

1. **所有権と競合が原子的に確保されていない。** `execute` は `read() == None` の後に別操作で `write(A)` し、削除前も `read() == B` の後に別操作で `delete()` する。UUID 名と照合は衝突確率を下げるが、その間の同名作成・変更は防止しない。影響: 他者が同一 target を操作した場合、既存値の上書きや他者値の削除が起こり得る。修正案: 条件付き作成・削除が利用できるか実 API に即して確認し、利用不可なら操作対象の排他が成立する専用プロファイル等の前提を具体的な証拠で確立する。成立しなければ実書込みしない。
2. **実行監督・異常終了後の復旧経路が未完成。** `verify-04.py` は live feature のビルドと禁止中バイナリの無引数起動のみ。実 OS 試験用の監督・子孫の識別／終了確認・記録失敗時の停止・異常終了後の対象限定の残留照合手順を実装または実行した証拠はない。`execute` は失敗時に自動 cleanup を行わず、A/B の値や journal が残り得る。影響: 終了状態不明のまま再実行や削除を行うと対象の所有権・状態を判断できない。修正案: 対象の実行体と終了を証明し、記録・読戻し・不明時停止・本人が識別できる残留調査と復旧を実 OS 書込み前に具体化し、合成障害と独立レビューを行う。OS 障害時の無条件終了保証は主張しない。
3. **禁止解除版は存在せず、現在版の承認を流用できない。** `LIVE_APPROVED` はコンパイル時定数 `false` で `main` は終了 2。実 OS 経路を動かすにはソース変更と再ビルドが必要であり、現行の固定値・実行順序・バイナリ・安全境界の確認はその新版を承認しない。影響: フラグ変更だけを根拠に実行すると未評価版で実 credential API に到達する。修正案: 有効化版を限定し、変更後の SHA、実体、journal と全停止条件、実行バイナリを改めて独立レビューしてから実行可否を判断する。

## 確認した範囲と non-blocking

- 模擬ログ `mock-test-03.log` SHA256 `7D06AA940287B921B2906C6F573AD41BB373FB8ED5F339BAAA9CB155541741F2` は `9 passed; 0 failed` を示す。対象９テストは模擬 store／journal の正常・衝突・記録失敗・書込み／削除応答不明、journal 識別・上書き拒否・パスの各ケースであり、実 Credential Manager・異常な OS 終了を実証しない。終了 0 は保存された `.exit` と作者記録であり、本担当が元プロセスを監督した証拠ではない。
- `reserve` は UUID 形式の service と固定 account を検査し、新規ファイルへ識別子を書き flush・`sync_all`・読戻し後に返す。各 stage も同期する。`validate_journal_path` は既存の親を canonicalize し専用 manifest ディレクトリと一致させ、最終要素は `create_new` で既存を拒否する。親ディレクトリの耐久性、ACL、junction の検査後変更と readback 後の改ざんは未証明。安全な作業場所と事前識別子・失敗時復旧の管理が依然必要。
- `live-build-04.log` は `keyring v3.6.3` を含む build 完了を示し、保存 `.exit` は 0。`disabled-gate-04.log` と `.exit` は無引数の禁止メッセージと 2 を示す。`verify-04.py` はそのバイナリを起動するが、本担当は元ビルド・元実行を監督していない。機能を無効にした版のテストであり、有効化した実 OS 経路の動作ではない。実行バイナリの SHA は作者結果に固定されておらず、後続の実行対象として扱う場合は新たに固定する必要がある。
- `verify-03.py` と `verify-04.py` は Cargo を timeout 付きで起動するが、これは模擬試験・ビルドの監督であり、OS 書込みを行う実行体とその子孫の停止・cleanup 監督の証拠ではない。テスト runner の子孫全体の終了も本レビューで独立観察していない。
