## 条件と根拠

1. Issue #3 を公開 GitHub REST の番号指定 GET で取得（HTTP 200）。Windows Credential Manager での登録・変更・削除・再起動後取得の実機検証と秘密非露出が要求される。提案は合成 service の OS API 試験を実アプリや実 PAT のライフサイクルと明確に区別しており、試験成功だけでは Issue 完了にならない。
2. 対象ソース `isolated_windows_credential_lifecycle` は UUID を試験内部で生成し、合成値の登録・更新・削除を実施する。書込み前の識別子外部登録は確認できず、先行結果が試験を未実施とした事実と整合する。提案は事前識別記録・読戻し、完全一致対象、NoEntry とエラーの区別、終了後の残留確認を定めている。
3. 提案は、事前不存在確認と UUID のみを原子的な所有権の証拠とせず、条件付き作成が利用できない場合は書込みを他者が行わない隔離環境を前提とし、不明なら停止する。予約・識別・開始・書込み・削除・後読取・監督者停止を分け、記録・登録失敗時の禁止と復旧条件を示す。`docs/instructions/work.md` の監督・秘密非出力・不明時書込み停止と矛盾しない。
4. モックで正常・衝突・応答不明・journal 障害・プロセス停止・対象不一致を検証し、実装とログの独立確認後に実 OS 操作を判断する依存関係がある。PID 単独を終了の証拠にせず、OS 障害時の無条件の終了保証も主張していない。
5. 所有範囲は設計資料のみ。対象結果は未追跡の実ファイルを確認し、削除対象なしと記載している。限定 `git status` は対象設計資料を未追跡とし、対象ソースに差分を示さなかった。全 workspace の変更・削除の網羅確認ではない。

- 実用上、専用 Windows ユーザーと名前空間への他者の書込み排除を証明できない環境では実試験を開始できない。これは未解決の実行条件であり、隔離を仮定して成功扱いにしない。後続担当は具体的な隔離証拠、実行体の開始前登録・許可信号、親の停止時の子の振る舞い、記録の flush と ACL、対象一致と cleanup の条件を実装・試験で示すこと。
