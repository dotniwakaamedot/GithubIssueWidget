# 文字化け・レビュー文書置換の独立分析

- 担当 `/root/assignment_failure`。既存文書を変更せず対象の実バイトと関係者の記録を確認した。元操作の再実行はしていない。
- 結論: `test-review-01.md` には実バイトとして ASCII `?` が 812 個あり、表示設定のみでは元の日本語を取り戻せない。作者はパイプ経由の置換を報告し、ツール呼出しに残った原文から新版を作成している。一方、Issue タイトルの文字化けは表示経路のどの境界で生じたか未特定である。

## 根拠と判定

1. `tasks/03/test-review-01.md` の SHA256 は指定値 `8FBDC1986DCB1033F5B9AFAB99918FAF03AE427DA9BE2A90D3FD813D38326718` と一致。1,622 bytes、厳格 UTF-8 復号成功、バイト `0x3F` が 812 個、復号後の U+FFFD は 0 個。UTF-8 として妥当であることは内容が正しい証明ではない。バイト列から置換された元文字を特定することはできない。
2. 作者 `/root/movement_review` は `tasks/03/test-review-02.md` に、PowerShell パイプで Python へ渡した日本語が `?` に置換され、旧ファイルからは復元できず、ツール呼出しに残る原文から新版を作成したと記録した。具体的な元コマンド・ツール原文の所在と置換の正確な境界は本分析では未確認。新版の内容が一次要求と実際のテスト結果を正確に反映するかは別途レビューが必要。
3. `/root/issue_review` の `questions/review-encoding-01.md` は、Python の API タイトル出力が `�` 等と表示されたことと、別操作で `PYTHONIOENCODING=utf-8` を指定すると可読だったことを記録する。表示経路の文字コード不一致は原因候補だが、入力・出力・端末の境界、出力生バイトと API 原データとの差は未確認。元 API の破損を示す証拠はない。
4. `/root/movement_review` は同じ新版に API 本文表示の文字化け１件と UTF-8 指定後の可読化を報告した。詳細な変換境界や対象1との同一原因は未確認。２件は共に表示経路の問題の可能性があるが、旧レビューの実バイト置換とは現象を分けて集計する。

## 再発防止と検証条件

- F-057 の既存対策は入出力の文字コードを明示し短い日本語を確認すること。表示失敗２件との関連および過去の累計・重複は管理側で照合する。旧レビューの実体置換は別の結果を持つため、表示だけの失敗にまとめず記録する。
- 新規日本語ファイルは入力から保存まで UTF-8 を指定できる経路を用い、保存後にファイル実体を厳格復号し、日本語の代表箇所を原文と照合する。`?` が元から存在しうるため件数のみで判定せず、意図した文章と照合する。既存策の効果は未検証。
- 旧文書のハッシュを保全して承認根拠に使わず、新版は利用可能な原文・対象版・テスト証拠を照合し、別担当が版と SHA を明示して独立再レビューする。元文面が照合できない箇所は未確認とし、推測で復元しない。
