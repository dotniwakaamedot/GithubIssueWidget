## 最小手順

1. 対象版と他の起動中ウィンドウを確認できたら対象 EXE を起動する。起動できたか、接続画面または一覧画面のどちらが表示されたかだけを報告。ウィンドウの移動・サイズ変更・最前面切替を各1回、許可された GitHub リンクを1回試し結果を記録する。閉じる操作では対象画面が消えたか記録する。エラー画面を共有する場合も秘密や非公開情報を隠す。
2. 接続が必要なら、本人の権限に応じた専用 fine-grained PAT を対象リポジトリに限定し、Metadata 読取と Issues 読書を付与して本人がアプリへ直接入力。既存保存値を使う場合は専用であることと上書き・復旧を先に確認する。画面に結果が出たら成功・失敗の一般的な表示だけ報告する。接続 GET の成功は書込み権限の証明ではない。
3. 接続成功後、本人が対象を確認したうえで一度閉じて同一 Windows ユーザーで再起動し、PAT を再入力せず一覧に接続できるか確認する。既存資格情報を置換・削除せず確認可能な場合に限る。表示・保存・復元を区別し、未実施を残す。
4. 書込み対象は既存承諾済みの公開 `dotniwakaamedot/GithubIssueWidget` の新しい検証用 Issue **1件のみ**。既存 Issue・PR は変更しない。作成前に対象 repo、使用するテスト用ラベルとアクセス権を確認し、不明なら書込みを保留する。識別しやすい一意の題名を決め、対象に Issue を1件作成し、番号と状態のみ報告。題名に個人情報や秘密を入れない。
5. 当該 Issue だけを To Do・In Progress・Done の全6方向へ移動し、各操作後に GitHub 上の open/closed と status、および既存の非 status ラベルを確認する。途中で失敗・状態不明なら次の操作を止め、GitHub 側の実状態を取得して報告する。作成応答が不明な場合は再作成せず、題名・時刻・一覧を照合する。最後にこの検証 Issue をクローズし履歴は保持する。ラベルが不足・権限不明なら作成や変更を進めない。
