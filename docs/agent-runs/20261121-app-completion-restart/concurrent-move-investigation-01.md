## 確認した事実

- `main.tsx:223` の drag start は対象の BoardIssue 一件を `draggedIssue.current` に保存し、drop はその一件を取り出して `moveIssue` を一度呼ぶ。`main.tsx:154–158` はその Issue の `number` を一つだけ `move_issue` に渡す。Rust `movement.rs:4` の実処理も番号一つを対象とし、status ラベルに対するループは同一 Issue のラベル操作である。読んだ範囲では一つの drop が複数番号を更新する処理は確認できない。これだけで実行時の現象を否定できない。
- `movingRef.current` は `await` より前に同期的に true となり、同一 App インスタンスの同時移動呼出を抑止する。移動中は `draggable` も無効になる。別ウィンドウ・プロセスを横断した排他の保証は、この ref からは導けない。
- `style.css:3` の Issue カードは列内の通常フローに並ぶ。移動したカードが抜けると同じ列の後続カードが詰まり、画面上の位置が変化する。これは複数 Issue の GitHub 状態が変更されることとは区別が必要。
- `main.test.tsx` のドラッグ試験は模擬イベントと模擬 API によるもので、実 WebView2 のイベント配送、実際のポインター操作や複数カード移動を証明しない。今回テスト・実 UI は実行していない。

## 識別と対応

追記: ユーザーは Todo / In Progress の文字が選択され複数選択されて一緒に動くように見えると説明した。現 CSS の `user-select:none` は `.titlebar` のみで、列見出しとカードには指定がない。通常の文字範囲選択が症状を説明する有力な仮説だが、実操作を直接観測していない。局所的に列見出しの静的テキストとカードへ `user-select:none` を適用する案がある。文字のコピーができなくなるため範囲を絞り、フォームやその他のテキスト選択は維持する。リンク・＋ボタン・キーボードフォーカス・カードドラッグを実 WebView2 で確認し、CSS 試験だけで実現象の解消とみなさない。

さらにユーザーは「＋ボタンが選ばれていると複数動きます」と訂正した。各列の「＋」は `h2` 内の button で `onClick` から `openCreate(status)` を呼び、移動対象の選択・追加処理はコード上確認できない。`style.css:4` で右に float し、選択色やドラッグ画像の実際の表示は静的読取りでは確認できない。「選ばれている」が文字選択・フォーカス・クリックのどれかは未確定。＋をクリックして作成画面が開く状態か、文字の選択色に含まれる状態か、また実際に別 Issue の列・GitHub 状態が変化したか画面上で一緒に付いてくる見た目だけかをユーザーに確認する。非公開内容を表示しない観察で識別できる。上記 CSS 案は引き続き仮説への対策であり、観察なしに解決済みとはしない。

画像 `C:/Users/semis/AppData/Local/Temp/orca-paste-1795239911813-b3226a45-238c-4d5f-8ba8-1e30b406eb85.png` を閲覧。In Progress 列の複数カードの文字に対応する半透明の像が各カードの下側にあり、＋ボタンは青い背景に見える。単一カードだけの見た目ではないが、画像のみでは半透明像の生成元、文字選択の有無、実 Issue の状態更新は断定できない。最小候補は `.board-column h2` と `.issue-card` に `user-select:none` を指定し選択範囲を抑えること。実 Windows / WebView2 で選択操作を含む再現の前後を比較し、ドラッグ画像と対象番号、実 GitHub 状態を確認する。フォームの選択・コピー、＋やリンクのクリック、キーボードフォーカスと移動を回帰確認する。選択抑制のためカード文字のコピーはできなくなる。必要なら `setDragImage` による対象カードだけの画像指定も検討するが、現時点では原因・必要性未証明。

ユーザーに #11 と一緒に動いた Issue の番号、および移動前後の列・GitHub 状態か、同じ列内の画面位置だけの変化かを確認する。共有時に Issue 本文や秘密は不要。実 API 更新の疑いがあれば対象と時刻のイベント履歴を読取り、表示の再配置と分ける。既存 Issue を操作して再現させず、認可された検証用 Issue を使う。原因が確定するまでは表示アニメーションや排他処理を追加しない。

別 Issue が更新される経路または期待と異なる画面位置変化が確認された場合は、その経路を対象に実装と回帰試験を設計する。別ウィンドウからの並行更新を防止する要望の場合は別の要件として同期範囲・解除・障害時挙動が必要になる。
