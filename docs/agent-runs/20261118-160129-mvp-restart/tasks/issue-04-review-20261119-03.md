## B01: 接続確認の GitHub 要求が共有レート待機を参照・更新しない

- 根拠: `widget/src-tauri/src/main.rs` の `get_api_response` は `process_lock` の下で `check_cooldown` を行い、レート制限を検出すると `record_cooldown` によって共有 `rate-limit.json` に期限を記録する。一方、同ファイル `verify_connection` は直接 `client.get(...).send()` し、`save_connection` は共有 lock を保持するものの `check_cooldown` を呼ばず、この要求の 403 / 429 から期限を記録もしない。
- 影響: 一覧要求が `Retry-After` や reset の待機期限を記録した直後でも、設定画面の「接続を確認して保存」は同じ GitHub API に要求を送れる。また接続確認そのものが制限応答を受けても、別ウィンドウや後続の一覧要求はその制限を知らない。GitHub は [レート制限の指針](https://docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api) で示された待機時間中に再要求しないよう案内しており、操作間・別プロセスを含む前回 B02 の防止は未完了。これは静的な制御フローの確認であり、本レビューでは実制限を発生させていない。
- 修正案: 設定確認を含む同一認証主体の全 GitHub 要求で、共有待機期限の確認・制限応答の記録を同じロック規約で適用する。すでに `save_connection` がロックを保持していることを考慮し、再入によるロック失敗を避ける。合成サーバーと別プロセスを使い、一覧→接続確認、接続確認→一覧、手動・自動、再起動の順序で期限前に要求されないことを確認する。
