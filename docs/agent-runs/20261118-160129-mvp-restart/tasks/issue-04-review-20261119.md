## B01: 別プロセスの接続先変更後に、旧接続先の見出しで新接続先の Issue を表示する

- 根拠: `widget/src/main.tsx` 32行は起動時に接続設定を読み取り、87行の見出しにその React state を使う。40行の `list_issues` には期待する接続先を渡していない。一方、`widget/src-tauri/src/main.rs` 73〜85行は呼出しごとに共有設定ファイルから現在の接続先とトークンを読む。別インスタンスが接続先を変更しても、最初のインスタンスの `connection` state と `requestVersion` は更新されない。設定のファイルロックは同時保存を制御するが、画面が持つ接続先と取得結果の対応を検証しない。
- 影響: A を表示しているインスタンスの次の同期が B の一覧を取得し、A の見出しの下に B の Issue を表示し得る。非公開 Issue を含む接続先の誤表示であり、#4 の切替前後の整合性と秘密保護に影響する。
- 修正案: 一覧取得要求・結果に接続先または変更世代を結び付け、描画時に表示中の確定接続先と一致する場合だけ採用する。別インスタンスによる変更時は状態を再読込するか不一致を通知し、旧ボードを消去する。2インスタンス相当の擬似テストを追加する。

## B02: 長時間のページ取得が60秒更新で繰り返し無効化される

- 根拠: `main.tsx` 37行で新たな同期を始めるたび `requestVersion` を進め、41行は最新の番号だけを採用する。46〜48行は前の取得の完了を待たず60秒ごとに新たな取得を開始する。`main.rs` 45〜69行はページを直列取得し、個々の HTTP 要求にはタイムアウトがあるものの、全ページの合計時間には60秒以内の保証がない。
- 影響: 1回の全ページ取得が毎回60秒以上かかると、最初の結果は次の同期で無効になり、後続も同様になってボードが完了表示に到達しない。取得が重複し API 呼出しも増える。多数の Issue や遅い通信で #4 の全件取得と同期に影響する可能性がある。
- 修正案: 同一接続先の同時同期を重複させず、完了後に次の同期を予定するか in-flight を共有する。接続先が変わった場合の破棄は維持する。60秒を超える遅延と複数ページで進行・結果を確認するテストを追加する。

## B03: 二次レート制限を識別せず、解除時刻前にも定期再試行する

- 根拠: `main.rs` 52〜55行は `x-ratelimit-remaining: 0` または HTTP 429 のみをレート制限と判定し、HTTP 403 の二次制限メッセージや `retry-after` を確認しない。`main.tsx` 47行の定期実行は応答の `retry-after` や `x-ratelimit-reset` に関係なく60秒ごとに続く。GitHub 公式は二次制限でも 403 または 429 が返り、`retry-after` があれば指定時間まで、主制限なら reset 時刻まで待つよう記載している。[GitHub REST API のレート制限](https://docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api)
- 影響: 二次制限の 403 が通常の権限エラーと区別できず、#4 の制限表示を満たさない場合がある。指定された待機期間より早い再要求を継続し得る。
- 修正案: 応答の必要なヘッダーと安全なエラー分類を扱い、primary・secondary を区別できる範囲で表示する。待機期限まで自動・手動再試行を抑止し、403 secondary、429、reset/retry-after を含む模擬テストを行う。レスポンス本文を無加工で UI やログへ転送しない。

## B04: 件数だけで最終ページを決め、GitHub の next 情報を確認しない

- 根拠: `main.rs` 57〜67行は取得配列が100件未満なら終了し、`Link` の `rel="next"` を読まない。GitHub 公式は次ページの判定に `Link` ヘッダーを用いる方法を示す。[GitHub REST API のページネーション](https://docs.github.com/en/rest/using-the-rest-api/using-pagination-in-the-rest-api)。作者の模擬サーバーは固定順序で応答を返し、短いページと `next` の組合せや要求されたページ番号を検証していない。
- 影響: 件数が指定した `per_page` より少なくても next がある応答を処理する場合、残りを取得せず全件取得として返す。実 GitHub が通常の Issues 応答でその状況を返すかは本レビューでは未検証であり、起きたと断定しない。
- 修正案: API のページネーション情報を検証して追跡し、不明・矛盾は全件成功と扱わない。認証先を固定し、next URL を使うなら同一の許可済みホスト・経路とループを検証する。短いページ＋next、最終ページ、ページ番号・複数ページ失敗のテストを追加する。
