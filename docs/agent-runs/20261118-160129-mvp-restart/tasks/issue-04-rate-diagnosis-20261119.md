## 確認した事実と原因の範囲

1. 初回 B03 は 403 二次制限、`retry-after` と `x-ratelimit-reset`、定期再試行が対象。第２回 B02 は `RateCooldown` のプロセスごとの独立が対象。第３回 B01 は一覧側に共有記録が導入された後も `verify_connection` が直接 `client.get(...).send()` する対象漏れを指摘する。後の指摘は前の修正で判明した別の漏れであり、実際に同じ GitHub 要求を繰り返して失敗した証拠ではない。
2. 第三レビュー対象版の `get_api_response` は `process_lock()` を取得して `check_cooldown` 後に送信し、制限と判定した応答から `record_cooldown` を呼ぶ。一方 `save_connection` はすでに `process_lock()` を保持してから `verify_connection` を呼び、後者は共有 cooldown を参照・更新しない。この静的経路から、一覧と接続確認のいずれかが制限されても他方に必ず伝わる保証がないと分かる。
3. `process_lock()` は同じロックファイルに `try_lock_exclusive` を使う。保持中の `save_connection` から、内部で再び同じロックを取得する既存 `get_api_response` をそのまま呼ぶと、再入ロックを取得できず失敗する可能性がある。同一プロセスのテストには別ハンドルの競合検査があるが、この具体的な呼び出し経路は実行していない。
4. [GitHub REST API のレート制限](https://docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api) は、主制限は 403 / 429 と残数 0、二次制限は 403 / 429 と制限を示すメッセージを返すと説明する。`retry-after` があればその秒数、残数 0 なら reset 時刻を待ち、いずれもなければ少なくとも１分待つ。二次制限が続く場合は待機を指数的に延長し、回数を制限するよう案内する。

## 修正案

- GitHub に送信する一覧・接続確認、将来の作成・更新を網羅する共通の要求処理で、送信前の待機確認、403 / 429 の分類、制限応答の共有期限記録を一貫させる。トークンや応答本文をログ・共有ファイル・UI エラーへ出さない。通常の 403 権限エラーも区別し、レート制限と断定できない応答はその不確実性を保つ。
- ロックの所有を明示する。例として、既存の設定変更 transaction が既に持つ guard を渡して送信する内部処理と、guard を一度だけ取得する外側の入口を分離する。`save_connection` からロック取得付き wrapper を再度呼ばない。別案として設定ロックとレートロックを分離する場合は全操作の取得順と crash 時の取扱いを定義する。どの案でも保護中に新トークンや設定が食い違わず、送信・制限記録の間に別プロセスが待機を迂回しないことを確認する。
- 共有期限は同一状態領域で atomically 保存し、既存値と新値の最大を保持する。読取・保存失敗、壊れた記録、時計の変更、同時応答、トークン変更や別プロセスの開始時の保守的な扱いを定める。書込み失敗で別プロセスまで抑止できると断定せず、エラーと未保証範囲を明示する。記録には期限等の必要最小限のみを置く。
- 自動・手動とも期限前にネットワークへ出ないようにし、一次 reset、retry-after、双方なし二次制限、通常 403、429 と、再度の二次制限での増加待機・上限を検証する。HTTP-date 形式については GitHub の文書の秒数案内と実装の対応範囲を区別し、未知形式を黙って短い待機とみなさない。
