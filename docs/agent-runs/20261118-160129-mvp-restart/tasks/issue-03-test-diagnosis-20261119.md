## 推奨する検証方法

1. **対象版の固定:** R01 の修正後、対象全ファイルと lockfile の SHA256、作業場所、ツール版を保存し、変更前後の一致を確認する。テストコマンド・終了コードと機密を含まない集計結果を同一の証拠に結び付ける。後からソースが変わったら新対象版として実施・レビューする。
2. **秘密のない隔離テスト:** 設定先と credential store、HTTP transport を依存注入できる境界に分け、ユニットテストではメモリ上の偽ストアと合成文字列のみ使用する。認証レスポンスを localhost の試験サーバーまたは transport のモックで返し、実 GitHub に送らない。HTTP の試験用差替えが製品ビルドで外部 URL や認証先を変更可能にしないことを別途検証する。正常系と上記異常系について、以前の設定と秘密の保持、参照切替、警告、秘密を含まない返却値を確認する。
3. **中断と復旧:** 秘密の値を記録せず、世代 ID と処理段階だけを持つ復旧方式を検討する。偽ストアで、復旧記録の永続化前後、新資格情報の書込み前後、設定切替前後、旧資格情報の削除前後、削除や復旧記録の更新失敗ごとに中断し、再起動相当の処理で参照中の資格情報を壊さず未参照世代を検出・回復または明示することを検証する。復旧中に再中断しても再実行できることを確認し、削除対象は当該アプリ・当該試験の既知 ID だけに限定する。
4. **Windows 実ストアの合成検証:** 本番サービス名・既存資格情報を使わず、テスト専用の一意な名前空間と合成値、隔離された設定ディレクトリを用意する。初回・更新・削除・再起動、二つの独立プロセスの排他を確認する。作成した個別エントリの追跡・検証後の扱いを開始前に定め、他の資格情報へ一切触れない。中断・失敗で残ったものは所有と対象を記録し、対象・適用指示・認可を確認するまで勝手に削除しない。合成試験の成功は実 PAT による接続成功を意味しない。
5. **UI と実接続:** モック IPC で初期読込、保存失敗後の状態再取得と不明表示、設定警告が他のウィンドウ操作で消えないことを回帰確認する。実 GitHub はユーザーが利用を認めた対象・権限の検証用接続で行い、PAT 自体は出力・保存用ファイル・スクリーンショットに記録しない。`GET /repos/{owner}/{repo}` の確認と実際の Issue 書込み権限の確認を混同しない。
6. **漏洩確認:** 固有の合成 sentinel をトークンとして利用し、対象範囲を定めて設定・復旧記録・テストの結果や IPC 返却文字列に含まれないことを検査する。失敗時も sentinel 自体を出力せず、検査対象と件数・合否のみ記録する。これだけで全メモリや全ログの秘密不存在を証明するものではない。
