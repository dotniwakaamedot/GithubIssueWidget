# Issue #6 GET〜PATCH 競合テストの独立調査

## 結論

第1回レビューでは競合の再現証跡自体がなく、第2回では追加されたテストが外部変更をコメント上で仮定するのみで、模擬サーバーの状態を変化させていなかった。どちらも GET と PATCH の間の他者変更が失われる事象を実際に検証していないという同種の不足である。テスト成功は、事象が再現された証拠にならない。

## 確認した事実

- 第2回レビュー対象 `movement.rs` の SHA256 は `86B328972B83C132A2A94309D7C5E23B339AF72CB2D013CDE347227268B5B747`。調査時の作業ファイルは他担当が並行修正しており、SHA256 は `80537200E6A9CFFBDA4958C6815908C91C11A39CB2524FBFF7BA8EC0D048B539` だった。競合テスト自体は、固定レスポンスと PATCH ペイロードの確認を行っている。
- `server` は指定されたレスポンスを順に返し、受信リクエストを保存するだけであり、Issue の可変なラベル集合を持たない。問題のテストでは GET の返答に `external` が含まれず、PATCH ペイロードに同ラベルがないことは確認しているが、外部追加・PATCH 適用前・適用後という状態の遷移は観測していない。
- 実装は取得した `updated_at` を比較した後、取得済みラベルから生成した完全なラベル配列を PATCH し、返答内容をその配列と比較する。その間に外部の追加があっても、コード上はその追加を認識できない。実 GitHub での競合再現やネットワーク実行は本調査ではしていない。

## 推奨する再現設計

1. ローカル模擬サーバーに Issue の可変状態を持たせ、初期値を `open`、`["bug", "status:todo"]`、更新日時 `v1` とする。対象 Issue の GET は、この初期状態のスナップショットを返す。
2. **GET 応答を作成・送信した後、PATCH を処理する前に**、模擬状態に `external` を追加し更新日時を `v2` に進める。追加直後の状態を別の証跡として保存し、実際に `["bug", "status:todo", "external"]` になったことを assert する。サーバースレッド上で PATCH の accept／処理より前に追加すれば順序が決まり、スリープで時間調整する必要はない。
3. PATCH の HTTP 本文を `Content-Length` まで読み、JSON を解析する。`state` と `labels` を受信した値で模擬サーバーの現在状態に適用し、更新日時を `v3` として、**適用後の可変状態から** API 返答を生成する。事前に固定した応答で済ませない。
4. サーバースレッドの終了後、実際の受信順序と PATCH が1回であること、送信ラベル、外部追加直後に `external` が存在したこと、適用後の状態から `external` が消え `bug` と `status:done` が残ったこと、`move_in_repo` がその模擬応答を成功と判断したことをそれぞれ assert する。模擬サーバーの PATCH がラベル配列を置換するというモデルの結果であることを明記し、実 GitHub での競合を検証したとは主張しない。
5. 対照として、GET が画面の日時と異なる場合に PATCH が送信されない既存テストを維持する。第2回レビューのもう一方の指摘である複数ステータスラベルの検証も6方向テストと別に維持する。

原因については、事象の前提をテスト名・コメントに記載し、実際の状態変化とその前後の観測を設計・照合しなかったことがコードから確認できる。作業者の内面的な理由は分からない。

## 範囲・教訓

対象ファイルと両レビューを存在確認して読み、静的に調査した。製品コードの編集、テスト実行、GitHub への書込みは行っていない。実装後は固定した版を再テストし、レビュー担当が実際の状態遷移を独立に照合する必要がある。

1. 再現テストでは、問題を起こす前提となる状態変更を明示的に実行し、その直後と操作後の両方を観測する。
