## 確認された事実

1. 両方の作業場所は `C:\Users\semis\orca\workspaces\GithubIssueWidget\issue-6-move-resume`。先の検索は `rg` の明示パスとして `widget/README*` を含み、Windows は OS error 123（ファイル名・ディレクトリ名またはボリュームラベルの構文不正）を返した。担当者はシェルがワイルドカードを展開すると期待しており、事前の列挙・存在確認をしていなかった。
2. 続く検索は `widget/README.md` と `README.md` を指定し、前者が見つからないという OS error 2 を返した。前者は事前確認せず推測したパスだった。両回とも終了コードは担当者が取得しておらず未確認。
3. その後、担当者はリポジトリ直下の `README.md` の存在を `Test-Path -LiteralPath` で確認し、読み取った。今回の調査では当時のコマンドログ全文を直接確認しておらず、実行内容とエラーは担当者の回答による。

## 同一性と原因

両件は **存在・解決先が確定していないパスを `rg` の検索対象に渡した失敗**として共通しており、ユーザーの失敗回数管理上は同じ種類として扱うのが妥当。一方、OS error 123 のワイルドカード構文と OS error 2 の不存在は異なる直接原因であり、同一の OS エラーや同一の具体的な誤操作だったとは断定しない。以前の `Get-Content` の `PathNotFound` ともツール・直接原因は異なるが、対象パスを確認せず参照したという上位の失敗類型は共通する。

## 再発防止

- 個別ファイルは作業場所と絶対または基点を明確にしたうえで `Test-Path -LiteralPath` を確認し、存在する場合だけ検索・読み取りする。存在しなければ制御されたメッセージを出し、推測した別パスを続けて渡さない。
- ファイル名が不明な場合は、既存であることを確認したディレクトリを `rg --files` で列挙してから選ぶ。Windows のネイティブコマンドに渡す明示パスでシェルのワイルドカード展開を前提にしない。検索対象の絞り込みが必要なら `rg` の `-g` を使用する。
- 一連のコマンドは、対象が正しく存在するかと終了コードをそれぞれ確認し、エラーの場合に元コマンド・cwd・標準エラー・終了コードを秘密情報を除いて記録する。
- 上記の判断と停止回数の確定は親担当が行う。調査後に同種の失敗が2回発生した場合は、ユーザー指定に従って停止する。
