## 指摘

### B01: Issue の着手条件と記録手順が欠ける（blocking）

- 根拠: `docs/issue-workflow.md`「二重着手と進行記録」は着手・再開前に担当、コメント、関連 PR、共有 run、worktree を照合し、ラベルと進行コメントの読戻し・再照合ができなければ実装しないと規定する。対象計画は #3〜#6 を直列実装すると記す一方、それぞれの着手前の照合・記録・読戻しと、GitHub 更新の認可または確認不能の場合の保留を実装順に組み込んでいない。読取時の #3〜#6 は `OPEN`、状態ラベルなしで本文は「調査・詳細化中」。
- 影響: 他の担当や既存作業と競合したまま着手、または必要な外部記録が未確認のまま進む可能性がある。ラベルだけで排他は保証されない。
- 修正案: 各 Issue への着手前後に全コメント・担当・PR・run・worktree と状態を照合し、適用指示に従い記録・読戻し・再照合を行う依存条件を追加する。認可・状態・所有者が確認不能なら対象作業は保護して保留し、独立した作業のみ継続する。各 Issue の完了条件と検証範囲を着手前に詳細化する。

### B02: Issue ごとの作業場所と統合基準が未定義（blocking）

- 根拠: `docs/issue-workflow.md`「計画、作業、再開」は承認済み基準から Issue ごとに新規ブランチと専用 worktree を作り、再開時に旧担当の停止・所有権を確認するよう規定する。対象計画は #2〜#6 をひとつの worktree に直列実装するとしており、Issue ごとの基準、作業場所、成果と統合先を指定しない。旧担当の現在の状態は未確定と記載されている。
- 影響: 各 Issue の対象版・独立レビュー・統合関係を再現できず、未完了の作業と後続変更が混ざり、旧担当との所有・競合も判断しにくい。
- 修正案: Issue ごとの基準 SHA・専用 branch/worktree・所有者・親の統合先を、前段で確認可能な段階ごとに特定する。旧担当の停止・所有権・引継ぎが確認できない範囲は変更しない。複数 Issue を同じ作業場所に置く特例を採る場合は、適用される指示を満たす根拠を示す。
