## B01: GitHub が実際に返す次ページ URL を拒否する

- 確認された事実: `widget/src-tauri/src/main.rs` の `has_next_page` は、next URL のパスが元の `/repos/{owner}/{repo}/issues` と完全一致し、query が `state`・`per_page`・`page` の3個のみであることを要求する。その後 `fetch_pages` は next URL 自体を使わず、元の endpoint と加算した page を使う。
- 独立観測: 2026-11-19 00:20 UTC 頃、認証情報を使わず公開リポジトリ `octocat/Spoon-Knife` の `GET https://api.github.com/repos/octocat/Spoon-Knife/issues?state=all&per_page=100&page=1` を実行し、終了コード 0・HTTP 200 と `Link: <https://api.github.com/repositories/1300192/issues?state=all&per_page=100&page=2&after=...>; rel="next"` を観測した。本文は `NUL` に出力し保存していない。GitHub 公式の [ページネーション資料](https://docs.github.com/en/rest/using-the-rest-api/using-pagination-in-the-rest-api) も `/repositories/<id>/issues` 形式の next を示す。
- 影響: 観測した正規の GitHub 応答はパス不一致および cursor パラメータ追加のため対象版に拒否される。したがって複数ページを持つ実リポジトリの一覧取得に失敗し、#4 の全ページ取得を満たさない。テストのローカル mock は元 endpoint と同じパス・3パラメータの URL を生成しているため、実応答との差異を検出できない。
- 修正案: GitHub が返す正規の next URL とカーソルを実際に扱い、`https://api.github.com`・許可する `/repositories/<検証済みID>/issues` 等・owner/repo との対応・禁止された authority/fragment・循環を検証する。リポジトリ ID の確認方法と情報漏えい防止を設計し、実際に観測された `repositories/<id>` と `after` を模した応答、悪意ある host/path、ループ、短いページと1000件超のテストを行う。

## B02: 別プロセスのレート制限状態が共有されない

- 根拠: `RateCooldown(AtomicU64)` は Tauri process ごとの `.manage(RateCooldown::default())` で作られ、実装上プロセス間の共有・永続化はない。前回の B01 に対して複数インスタンスが同じ設定とトークンを読む設計を想定し、設定のロックはあるが、`fetch_pages` には別インスタンスの待機期限が渡らない。
- 影響: 同一トークンでウィンドウ A が rate limit と `Retry-After` を受けても、既に稼働中または新規起動したウィンドウ B は待機期限を知らず要求し得る。GitHub は同じ制限の待機時間中に再要求を控えるよう案内する。[GitHub REST API のレート制限](https://docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api)。これはコードの分析であり、実アカウントのレート制限を再現したものではない。
- 修正案: 単一インスタンスに制限するか、同一状態領域のプロセス間で待機期限を共有・同期する。設定変更と資格情報の区別、同時の制限応答、再起動、手動・自動更新を考慮し、2プロセスで実通信なしに再要求抑止を検証する。待機状態に秘密を記録しない。
