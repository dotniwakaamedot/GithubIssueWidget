# Issue 作成の実 GitHub 検証準備

- ユーザー指定・許可: `dotniwakaamedot/orcaDiversion` でテスト Issue の作成・状態変更。既存 Issue は変更しない。`status:todo`、`status:in-progress`、`status:done` はユーザーの明示許可により追加・読戻し済み。削除は許可されておらず行わない。
- 目的: レビューを受けた対象版の実作成処理と GitHub の Issue・ラベルを照合し、後続の状態変更検証に同一テスト Issue を利用する。アプリの実 UI・Fine-grained PAT・全障害経路の証明とは区別する。
- 予定の一意識別子: `github-issue-widget-test-20261119-create-01`。テスト Issue のタイトル・本文に検証目的と識別子を含め、公開先に不要な情報を送らない。送信前に指定先・権限・ラベル・open/closed の既存同一識別子を確認し、重複または不明なら作成しない。
- アプリと同じ Rust の作成関数を対象版テストから一度だけ呼び出す案。既存 `gh` の認証をプロセス内で一時利用する場合、トークンを標準出力・ログ・ソース・設定・証拠に出さず、環境変数は `finally` で元の状態へ戻す。ユーザーがトークンをチャットに入力する必要はない。認証方式は Fine-grained PAT とは限らないため区別する。
- 作成前に検証専用の新しい状態ディレクトリと `pending-issue.json` の不存在を確認する。操作結果、対象 SHA、Issue 番号・URL、HTTP と状態ラベル、未確認を記録する。通信断・不明応答・記録保存失敗では自動再試行しない。識別子と公開 API で既存 Issue を照合し、成否が不明のまま追加 POST しない。
- 利用するテスト用コードと入力・所有範囲を固定して独立レビューする。Issue #5 の実装レビュー blocking の解消前には実行しない。テスト Issue の削除や他の Issue の編集は行わない。テストが終わるまで同 Issue と記録を保持する。
