# 依頼情報の構造化と照合方式案 01

## 背景と確認された範囲

- 確定前の同じ包括メッセージを出す内容検査が2回失敗したため、該当操作を中断し別担当に調査を依頼した。
- 独立調査で、1件目は必須担当 ID の本文記載が欠けていたことを確認。2件目は日本語の言い回しと部分文字列検査の不一致の可能性があるが、未保存の原稿があり確定できない。
- 別の履歴として、存在しないパス参照の問題が3回で中止され、その後の再開で基点取違え1回が報告されている。過去の移動操作・文字破損も保護し同経路を再試行しない。

## 提案: 入力データと文章を一体化する

1. 管理が依頼ごとに、担当 ID、作者 ID、結果の相対パス、各固定参照の基点・相対パス、履歴イベントと分類、今回の各分類の件数、閾値、ユーザー原文を、単一の構造化データとして用意する。宛先と権限は必須項目とし、ID は実際の担当割当と照合してから使う。
2. ハッシュは参照先の実体から取得し、先に基点と相対パスを分離し、全パス存在・通常ファイル・参照関係・64桁形式を確認する。複数基点の注記をパスに含めない。存在確認の失敗は個別に記録し、その参照の計算と依頼確定を停止する。
3. 停止条件・履歴件数・担当 ID・対象パス・SHA は、同じ構造化データから所定のラベルとともに生成する。文章の自由な表現で値を別入力しない。各値がデータと一致するかは文書全体の曖昧な部分一致ではなく、生成した固定フィールドを抽出・型検証して比較する。ユーザーの原文は値を加工せず別欄へ記載する。
4. 計画や結果本文の自由記述は入力データの付属とし、権限・安全条件・完了条件・残リスクは担当範囲と元資料から別途確認する。構造検査の成功は仕様の完全性や安全性の承認を意味しない。
5. 検査は入力形式、担当 ID の存在・一致、出力先の存在、各参照の基点・存在、SHA 形式・実体一致、履歴分類・件数・閾値、UTF-8 と発行後の内容の各項目を独立に診断する。問題時は項目名と値・期待値を必要な範囲で表示し、資格情報や private データは表示しない。どこかに不備があれば依存する書込み・送信・担当起動をしない。
6. 同一ディレクトリで一時ファイルを作成し、固定フィールド・実体ハッシュを確定前に検査、公開後も同じ構造化データと実体を照合する。参照対象が変化した場合は対象版の再固定・再レビューを行う。中間ファイルと既存成果は所有者を確認し勝手に削除しない。

## 安全条件と適用前の確認

- 本方式は設計案であり、コード・自動化ツール・既存ルールの変更はまだ行わない。別担当が、ユーザー原文との整合、履歴の数え方、固定データの更新権限、パスの解決とロックの限界、出力の可読性、既存の失敗を再発させないことを独立にレビューする。
- 同種問題が初回を含め2回生じたら該当操作を中断して別担当に客観調査を依頼し、同種3回で全作業を中止する。停止の判断を検証スクリプト任せにしない。
- 二つの検査失敗は初回を含め2件として保護的に扱う。調査済みでも同種3件目が発生すれば中止する。実際にどの失敗が同種かは根拠とともに親が判断する。
- 成果物はこの設計案のみ。依頼書の作成・担当再起動・製品変更・GitHub 更新は行っていない。
