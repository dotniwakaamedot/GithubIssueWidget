## 要件と判断

Issue #4 は「60 秒ごとに更新し、切替前の接続先から遅れて届いた応答が新しいボードへ反映されない」と明記。これは通常動作中、60 秒間隔で更新を開始することを自然に意味し、完了後にさらに 60 秒待つとは読めない。`main.tsx` 107–119 行では取得の `finally` で `setTimeout(refresh, 60_000)` を予約するため、取得に 10 秒かかる場合は開始間隔が 70 秒、長時間かかればさらに遅れる。60秒ごとの原文と実装の差異は確認済み。README と画面の「完了後60秒」は実装の説明であり Issue の要件変更の証拠ではない。

取得中の重複禁止と固定周期は遅い応答で両立できないため、進行中は次回開始を重ねず、完了時に期日経過を確認し必要なら直ちに一回だけ開始、通常時は開始から60秒後に更新する設計を推奨する。障害による API 制限はバックエンドのクールダウンを維持し、無限即時再試行を避ける。要求が最大遅延60秒保証なのかは未指定であり、実装・実環境制約を明記する。

## 応答の抑止と重複

切替時 `openSettings` がバージョンを進めてカードを消し、effect の cleanup は `active=false`、バージョン進行とタイマー消去を行う。完了した取得は両条件で書込みを制限する。旧取得完了後に新カードが残るケースは `main.test.tsx` の `ignores an old repository response after switching connection` がモックで検査。実接続と Windows の競合は未検証。

現行の定期タイマー自身は前回完了後にしか予約しないため重複しないが、取得中の移動または作成が完了すると `boardEpoch` が増え、古い effect は cleanup され、新 effect は旧 `invoke` の終了を待たずに次の `list_issues` を発行する（`main.tsx` 104–120、157–163、189–191 行）。切替でも同様に別接続の取得が並行し得る。古い応答の UI 反映は抑止されるが、全トリガー間での通信重複抑止は実現していない。Issue #4 は通信の重複禁止を明記しておらず、これは過剰通信・レート制限に関する設計上の懸念であって直ちに明文違反とは断定しない。接続切替を旧接続応答により長時間待たせないことも必要なので、単純な全体直列化は避ける。

エラー時は `issues=[]` と `boardError` を設定し不完全な既存表示を消す。次回は失敗完了60秒後。競合により失効した成功・失敗の双方は反映されない。`clears the board when another instance changes the connection` は失敗時消去を検査するが、一般通信エラー、レート制限、復帰までのタイマー、古い失敗が新画面を消さないことはこの監査対象の既存テストからは証明できない。

## 推奨する回帰ケース

1. 偽物の時計で開始から10秒後に取得を解決し、開始から59,999msで1回、60,000msで2回目を確認。従来実装なら70秒まで開始されず失敗する。
2. 取得を60秒以上保持し重複なし、完了後に期限切れ分を最大1回実行し、複数回分を一斉に発行しないこと。繰返し失敗時にも無限即時リトライしないこと。
3. 移動・作成完了と同時に進行中の取得がある場合、同一接続の呼出数と最新状態取得を確認。複数要求の統合またはキャンセルの挙動を設計で決める。
4. 旧接続の遅い成功・失敗を、新接続の成功後と失敗後に解決し、新画面・エラー・タイマーを上書きしないこと。設定画面への移動・アンマウント後に再取得されないこと。
5. 通信エラー・レート制限後にカードが消えてメッセージが残り、復旧後の成功でエラーが消え最新カードが表示されること。実 API の制限と復帰は別途検証。

既存テスト `refreshes the active board after sixty seconds` は即時解決のみ、`does not overlap refreshes when a request takes longer than sixty seconds` は完了から60秒待つ現行仕様を固定するため、要件に沿う新仕様に合わせ置換が必要。100件超・1000件超・分類・GitHub 実操作は本静的監査の範囲外。調査時のコマンド失敗なし。製品ファイル変更なし。
