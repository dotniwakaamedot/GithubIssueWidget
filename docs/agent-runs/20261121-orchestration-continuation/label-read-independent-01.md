# GitHub ラベル読取り失敗の独立調査

担当 `/root/existing_work_review`、前担当 `/root/issue_survey` とは別。実ラベルの作成・変更・実 credential の読取りや出力はしていない。

## 結論

`status:in-progress` はコネクタによる Issue #4 の取得に付随するラベルから存在を確認済み。`status:todo` と `status:done` の**現在の存在は未確認**。過去の確認記録はあるが現在の証明にはならず、取得失敗をラベルの不存在と扱わない。MVP 起動をこれだけで止める必要はなく、接続後にアプリが GitHub のラベルを直接確認し、不足・アクセス不能を明示する方式を活用できる。実際の書込みや作成に進む前には、対象と権限を再確認する。

## 原因と観測範囲

- 前担当からの報告によると、GitHub コネクタの汎用 fetch はラベル単体 REST endpoint を許可せず `HTTP 400 / INVALID_ARGUMENT`。このエラーはコネクタの引数・許可 endpoint に関する拒否であり、GitHub 上のラベル不在の証拠ではない。実際のコネクタ内部の拒否理由は未確認。
- 前担当は web の公開 API で3ラベルを**1回の呼出し内**で取得しようとしたが、3結果とも inaccessible / Internal Error。HTTP 状態は未確認。3件を独立した3回の再試行や GitHub 404 とみなさない。
- 独立調査で利用可能な GitHub コネクタのラベル関連ツールを確認したところ、追加・削除はあるが直接の一覧・取得ツールは見つからなかった。公開 GitHub の labels HTML ページを web の別経路で一度取得したが `Cache miss`、HTTP 状態は未確認。CUA の in-app browser で同ページを開く代替を一度試みたが `browser access host is unavailable` で表示に至らず、ブラウザーの変更・データ書込みはしていない。これらの原因は特定できていない。
- 前担当の観測は担当からの報告と先行記録による。元レスポンスの生データや認証情報は保存・再出力していない。検索で空を返した過去の `search_issues` はフィルター適用が不明であり、全ラベルの不存在の証拠には使えない。

## 過剰な再試行を避けた次の手

1. 既存の公開 Issue をコネクタで直接読む経路が利用でき、付いているラベルの存在は証明できる。付いていないラベルの不存在は証明できない。連続した API や web の再試行を繰り返さない。
2. ユーザーが通常の GitHub を確認でき、かつその確認が必要になった場合、対象リポジトリの labels 一覧で `status:todo`、`status:in-progress`、`status:done` の存在だけを確認する。トークン、アカウント情報や私的 Issue の共有は不要。通常の環境をエージェントが利用できるなら本人の操作を求めずに確認する。
3. アプリの設定後、ユーザーが所有する対象を選択しラベル存在確認を含む実際の作成・移動経路でアクセス可能かを確認する。値を操作する前の GitHub 読取りと、ラベル不足・権限不足時の停止を確認し、ラベルを勝手に作らない。実データの操作は既存の限定承諾・対象確認と安全な実行方式に従う。接続テスト成功だけでは Issues 書込み権限を証明しない。

この調査では原因を API・ネットワーク・ホストのどれかに断定できず、2ラベルを実際に読取れなかった。追加で発生した web `Cache miss` と CUA の browser host 利用不可を管理へ記録依頼する。同じ経路を再試行していない。解消には実際に利用可能な GitHub 読取り環境の回復か、ユーザーの通常環境での確認が必要。
