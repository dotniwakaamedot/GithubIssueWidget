## 実行前の固定案

1. 管理が専用・空の作業場所を workspace 内に予約し、既存 checkout と旧 fixture・既存キャッシュ・旧 worktree に書込まない所有範囲を固定する。そこへ現 `widget` の必要なソース、`style.css`、設定・package/lock を複写し、2対象のみ上記隔離版を配置。対象元と複写後の SHA、ファイル一覧、欠け・余分なファイル、改行・文字コードを確認する。複写前後に出典 SHA を再計算し、違えば止めて新版から再調査する。
2. 依存はネットワーク取得や共通 `node_modules` への書込みを避けるため、必要なインストール済み依存を専用領域へ**通常ファイルとして複写**する案。junction・symlink や hardlink で元へ書き戻す経路を許容しない。コピー対象のリンク・実体・容量・依存の完全性・許可とハッシュを実行前に検査し、固定できなければ実行しない。実際の依存構造・全副作用は未確認でありこの案は検証を要する。別途、指定 lock から隔離インストールする案もあるが通信・供給源・スクリプトと外部副作用の明示的検討が必要。
3. 作業ディレクトリを隔離 widget、TEMP/TMP・Vite/Vitest cache・ログ・出力をそれぞれ専用予約領域へ固定。実行前に設定・CLI で対応する指定が有効か、既定の `node_modules` 等へ書込まないかをバージョン固定の資料・合成チェックと独立レビューで確認する。ネットワーク・Credential Manager・実 GitHub・GUI を使わず、モック入力のみとする。秘密が含まれる環境変数や外部応答をログに出さない。
4. 実行経路は実体が確認された Node と、隔離依存内の Vitest CLI を直接指定。明示的な単一 worker と有限のテストタイムアウトを選び、`main.test.tsx` だけを一回実行する。正確な CLI オプションと対応版は**実行前に読取りで確かめる**。`npm ci`、watch、共有キャッシュ消去や旧残存探索を試験コマンドへ混ぜない。テスト本体は子を作らないが Node、worker、esbuild は別の子孫として扱う。

## 監督・判定・復旧

- 新試験のプロセスは予約済み専用監督者から生成し、実行ファイルと固定版、親子関係、開始時刻、権限、出力先を起動前に記録する。開始時の登録と実行再開・終了確認の競合を閉じる具体方式を選び、失敗・監督者停止・不明時の対応を固定して独立レビューする。Windows Job の単純な生成成功は子の所属や終了の証拠にならず、未所属の窓を含む方式検証が必要。旧合成子と新規子孫を名前だけで同定・終了しない。
- 有限の全体期限と出力上限を設け、stdout/stderr の排出を詰まらせず固定ログへ保存。正常時も root の終了コード、該当テストの実行件数・成功/失敗、監督対象の子孫終了を確認する。0件や出力途切れ、期限超過、子孫の状態不明は不成功・未確認。起動前失敗は生成有無を照合し、終了不明時は次回起動・共有先への統合・領域削除を止め、所有するログと状態を保全し調査を別担当へ依頼する。未知の旧プロセスや他人のものを終了しない。
- 試験は全フロントエンドテストの成功に加え、10秒応答後の開始60秒、60秒超で重複しないことと完了後一回再開、高速失敗から復帰、旧接続の成功・失敗抑止、unmount 後停止と説明文を確認する。合成テストは実 UI、実 API、スリープ・時計変更の代替にはならない。実行後は入力 SHA と出力先を再確認し、前後で保護対象が変わらないことを照合する。

## 統合への経路

現 checkout への変更は `sync-fix-plan-02.md` の開始前ゲートが有効であり、旧担当停止・移管および関連 PR 照合が不明な現時点では保留する。無期限に他セッション全体の不在証明を求める代わりに、旧 worktree や PR を**変更せず保護**し、隔離コピーで検討・試験を進める。統合可能にするには、管理が利用可能な authoritative 手段で具体的な旧担当の終了・移管と関連 PR を照会し、結果不明を解消するか、適用指示に従った変更管理上の判断を記録する。制約を勝手に解除しない。

条件が満たされた後、統合直前に対象 SHA・差分・未追跡・旧 worktree と PR の状態を再取得し、他者の変更があれば上書きせず再基準化・競合解消・再試験・新版レビューを行う。隔離版と出典の差分、試験対象の SHA、証拠を別担当が確認し、blocking がない対象版を最小差分として統合。統合後の実ファイル SHA を再検証・独立レビューし、レビュー時から変化があれば旧承認を流用しない。複数担当による書込み範囲は重ならないよう管理が直列化する。

未完了の間は固定 SHA の静的レビュー、テストケースの妥当性、依存・監督方式の資料調査、PR・旧作業の読取り照合を進められる。上記の隔離構成、監督方式、CLI 指定、旧プロセスとの独立性はすべて設計案であり未実証。
