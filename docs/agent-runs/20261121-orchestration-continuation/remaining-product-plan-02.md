## 依存と独立して進める作業

1. **現状・要件の固定**: GitHub から開閉を含む Issue を終端まで確認し、指定 #1〜#7 の本文・コメント・最新状態と PR を取得可能な範囲で再照合。失敗や短いページを終端・不在とみなさない。旧 run や同一ファイルの担当・変更を確認し、必要な更新を保護する。
2. **独立コード・合成テスト**: #6 の単一 PATCH 希望とラベル保持・競合の差、#3 の保存/復旧、#4 の100件超・1,000件超の複数ページ、Open/Closed・PR除外・途中失敗をそれぞれ固定版で確認。大量ページは既存テストの網羅範囲と合成入力を先に監査し、不足する場合は独立した実行方式・対象版を固定して早期に合成検証する。合成で実 GitHub の挙動を保証しない。所有範囲を分けた読取りレビューから具体的な不足を出し、変更が必要な場合は版別計画・担当・テスト・独立レビューを経る。GUI 不明だけを理由に無関係な静的調査や限定モック試験を一律に止めない。
3. **Windows GUI の失敗解決**: 別担当による F-078 の記録と現行版を照合し、既存の 101/panic/WebView2 記録から確定できる事実・不明を区別。旧の合成子の終了不明を理由なく終了扱いせず、専用領域の通常の安全な起動・終了観測、失敗時の出力保護と残余リスクを実際の対象に応じて設計しレビュー。自己製監督器の完成自体を目標化せず、許される範囲の実動作確認へ進む。
4. **実 API・認証**: 実用の認証方法と検証対象を確認。既存承諾は公開 repo で検証用 Issue 1件の作成・移動・クローズに限定され、現在の権限・対象・既存 Issue 保護・実行結果不明時の重複防止を別に確認する。実資格情報は安全な既存の仕組みから扱い、記録に含めない。実操作の前に操作ごとの方式を独立レビューする。
5. **統合・完成監査**: 作業者と異なる担当が各変更と現行ハッシュ・結果をレビュー。全要件に証拠を対応させ、未実施・未確認・失敗を完了に含めない。旧作業・未完了 PR が不明な点は不在と扱わず、競合を保護しつつ権限に沿って統合・後続検証を進める。完成後の整理確認は親が一度だけ行う。
