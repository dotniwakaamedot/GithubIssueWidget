# 担当 ID 取り違えの独立調査

担当 `/root/process_safety`。親と進行管理補助による割当の当事者ではないが、監督器・移動 Rust の旧指定担当として直接影響を受けた。`assignment-conflict-record-01.md`、管理担当の `assignment-conflict-answer-01.md` と各訂正依頼を照合した。元の全通知と正確な時刻は当担当から確認できず、以下は確定資料と直接経験に基づく。

## 確認事実と影響

| 対象 | 依頼に記載された担当と後の訂正 | 確認できた影響 |

いずれも作業の中断、再割当、確認という追加作業が発生した。**成果の上書きやテストの二重実行は、確認した資料では見つかっていない**。旧成果の利用と権限移管が常に正しく完了したとまでは判断しない。

## 原因と確度

管理担当の回答では、親と管理補助が同じ作業の担当を並行に決め、管理補助は依頼ファイルの確定・通知後に親から別 ID を受け取った。提示された依頼と訂正はこの説明に整合する。単一の確定担当を両者が通知前に照合する工程が成立していなかったことが再発に共通する運用上の要因と考えられる。個人の内面、ツール配信順序や具体的な内部原因は未確認であり断定しない。

## 文書負担を増やさない対策

既存の進行表の各行に、タスク ID、**正規担当 ID**、所有範囲／結果先、状態の4点を置き、親を割当の唯一の確定者とする。管理補助は新しい別帳票を作らず既存行を更新し、**通知前に親が確定した行と送信先を照合**する。担当名の相対表記を推測せず、実際の `spawn_agent` または `list_agents` の正規 ID をそのまま使う。行が未確定・不一致なら送信を待つ。

移管は同じ行で新旧担当を更新し、旧担当の停止と保護すべき成果を確認してから通知する。結果パスが既に使われていれば上書きせず新しい固有名を指定する。レビューの担当は作者と別であることを同時に確認し、重複レビューが必要か親が判断する。既存の依頼ファイルが必要な作業だけにファイルを作り、照合結果のためだけに毎回別ファイルを増やさない。適用例を次回の実際の担当通知で確認し、その結果を進行表へ短く残す。実践と再発防止効果は未検証。

## 調査中の失敗

run 配下を `rg --files` で列挙した際、`gui-release-build-01` がアクセス拒否となり、一覧は部分結果だった。失敗を不存在の根拠にせず、その後は既知の正確なファイルを個別に読み取った。対象探索時は生成・権限不明領域を除き、親と既知の正確なパスを先に確認する。共有失敗記録への追記は管理担当に依頼済み。製品・既存成果・外部サービスは変更していない。
