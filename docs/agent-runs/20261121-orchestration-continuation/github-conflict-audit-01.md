# GitHub 更新優先の現行挙動照合

担当 `/root/project_survey`。一次 Issue #6 を GitHub コネクタで取得。現行 `movement.rs` SHA `ED49F4BA52C6887BCE427E4A6664D335092A1C3311E1B1ED61B4CE322791ABA5`、`main.tsx` `6FCF2A34145450C5029B7FF80DDB3EC1DA5E27173AAB84E57F16D6D54C0E6A3E`、`main.test.tsx` `3123D7B77EA1E283082FDFF198BA882ACA1E0AAF216E9D7D567F20B55D615B63`。読み取りのみでテスト再実行や実 GitHub 書込みはしていない。

## 確認できた挙動

- 直前 GET の `updated_at` が画面時点と違えば、エラーを返してラベル・状態を書かない。UI はエラーを保持し finally で一覧再取得を開始。失敗後に同じ変更を自動再試行しない。実際の競合通知・再取得はモックや限定的 Rust 試験の範囲であり、実 GitHub・実画面では未確認。
- 最新ラベルを取得してから必要なステータスラベルを個別追加・削除、必要なら状態 PATCH、最終 GET で状態とラベルを確認。非ステータスラベルを配列で全置換しない。複数操作の途中拒否・不明応答や最終 GET 失敗では部分反映の可能性を表示する。Issue の「可能な限り一度の PATCH」とは異なる方式であり、中間・部分状態がある。
- UI は移動の成功・失敗後とも一覧を再取得し、一覧失敗なら `setIssues([])` で古いカードを消し取得エラーと移動エラーを別々に表示する。対象版の「移動不明＋一覧失敗」のモック1件成功は `movement-ui-execution-result-01.md`、固定版レビューは `movement-ui-execution-review-02.md`。再取得中は既存カードが一時表示されるが同期中表示がある。実 UI は未確認。
- 検知できる競合で再試行しないことと、GitHub の状態を常に勝たせることは別。初回 GET 後の外部の state/status 変更は当方の個別操作と競合し、途中の書込みを完全に防げない。最終値が偶然一致する競合や最終 GET 後の変更も検知できない。条件付き書込みを保証する仕組みは現コードにないため、「すべて上書きしない」「GitHub が常に勝つ」とは言えない。

## MVP に必要な差と最小案

**確認済みの通知不足**: 更新後の最終 GET が成功して状態またはステータスが一致しない場合、現行 `movement.rs` は「更新後の状態またはラベルが一致しません。最新状態を確認してください。」と返すが、その前の書込みが成功済みであり得ることを明示しない。最新のユーザー方針は途中反映の可能性の明示を求めている。最小修正はこの不一致エラーに「更新の一部が反映された可能性があります」を追加し、UI の既存再取得を活用すること。競合を完全防止できるとは主張しない。

既存隔離案 `movement-rust-regression-result-03.md` は同文言追加と3ケースを持つが、現製品に未統合。同版の実行は `movement-rust-execution-result-02.md` では0件収集であり成功証拠ではない。別の新 target 実行結果・レビューの有無は本監査では確認していない。既合格の同一試験の無条件反復はせず、固定版の新規差分と利用可能な試験証拠を確認してから最小修正を別担当へ割り当てる。

先行 `movement-audit-review-01.md` は旧テスト版に対する静的レビューで、最終不一致通知と race の限界を示す。今回の現行製品への修正・統合や全 Issue の完成を承認するものではない。実 GitHub の6方向・競合・部分反映、実 Windows UI は未検証。
