# MVP を通常の対話デスクトップで確認する経路

担当 `/root/existing_work_review`。read-only。既存の GUI・プロセス・設定を操作していない。

**CUA は通常デスクトップ上の他アプリを列挙できるが、実行中の対象 GUI を識別できていない。** 直近診断は `before_run` のみで、未到達・記録失敗・非同期処理未完了を区別できない。対話 session 2 と同じ番号の PowerShell が存在することも、対象窓と CUA が同じ desktop にある証明ではない。別環境や VM が利用可能という証拠は現時点でない。

現 release `23C383EB2E46CB205E052A9D4A24EE73B968EB2C776F7150826350685419B306` はビルド時点の版であり、現在の製品 movement SHA `88BF21BB45C077DFDA592D906C753D168C5641E35EB12324D4ACF1652374695B` の統合より前のため、最新改善を含むことは証明できない。現 main SHA `AEFF1E65AD93EFA04773CEBBB9736A6BDC5B9938DB9FAF937DD88B3D9CBFE86F`、React main `6FCF2A34145450C5029B7FF80DDB3EC1DA5E27173AAB84E57F16D6D54C0E6A3E`。この値は観測時点。先行 build の専用領域は ACL 制限があり、ユーザーから実行できるとは確認できていない。

次の実行可能な手順:

1. 起動担当の保持中対象の直接終了と結果を先に確認し、原因・対象を不明としたまま重複起動しない。既存の無情報起動を同条件で反復しない。
2. 最新の製品版を含む実行可能 EXE を既存の成功した release ビルド方式で更新し、出典 SHA・実行ファイル SHA を固定する。既存の合格テストは繰り返さず、既存設定・credential・旧対象を保護する。WebView2 が通常対話ユーザーで起動可能か、登録・利用の証拠を読み取りで確認する。
3. 対話デスクトップの正しいユーザー文脈で起動できる、既に利用可能な方法を優先する。CUA が対象の実 HWND を列挙できるなら、その ID と起動対象の対応を確認して画面を観察し通常終了する。CUA は在庫から既知の app/window を選ぶ手順を提供するが、対象アプリが在庫に現れないまま任意の HWND を選ぶ方法や、この sandbox のプロセスを通常ユーザー desktop で起動できる正式機構は確認できていない。ユーザー設定の変更や未確認の他プロセス操作はしない。
4. エージェント側で正しい desktop に起動する手段がないと判明した場合に限り、**固定した、ユーザーが読取・実行できる EXE を用意してから**、ユーザーに Explorer でその EXE を一度開き、表示かエラーかだけを知らせてもらう。現時点の制限付き旧 EXE パスを渡して起動可能と断定しない。開かない場合は同じ手順を繰り返さず、内容を安全に要約してもらう。画面の機密情報や PAT を送らせない。本人操作が実際に必要かは上記の環境確認まで未確定。
5. 表示できた後、接続先・PAT は本人がアプリに直接入力し、入力中の画面観察・記録を停止。既承諾の公開テスト対象で作成・移動・GitHub 上の再取得を、必要な権限と実行方式の確認後に進める。認証情報は会話に共有させない。

判断を妨げるものは「ユーザーの協力が絶対必要」と確定した状態ではなく、現在利用できる CUA・起動対象の対応と通常ユーザーでの実行可能性が未証明ということ。現時点で必要な操作を先に具体化し、不足証拠のみを確認する。実 GUI・PAT・GitHub 作成/移動は未検証。本調査では新しい失敗を認識していない。
