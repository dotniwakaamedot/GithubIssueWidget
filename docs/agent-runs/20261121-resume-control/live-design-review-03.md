## 確認結果と残る論点

1. **子プロセス上限は未検証。** `creation.rs` の対象テストは `reqwest` の client を `timeout(20秒)`、redirect 無効、retry 無効で構築することを静的に確認した。ただし呼出し先・依存ライブラリを含む全プロセス構成、`gh auth token` とその認証方式が子プロセスを使わないこと、対象バイナリとの一致は未確認。コード検索の一部が切り詰められ、全体検索の結果を根拠に不在とは判断できない。`ActiveProcessLimit=1` が子生成の拒否と整合して動作すること、既存 Job・入れ子や breakaway の影響は、環境と対象版を固定し秘密を使わない合成試験および独立観測が必要。実行時観測が書込み開始後では遅いため、制限の有効性と対象プログラムの適合を事前に確かめる。
2. **監視だけで異常終了を保証できない。** プロセス数を限定し外側の独立したハンドルで終了を確認する方向は、前回未証明だった子孫追跡を減らす候補だが、実装・検証されていない。代入・再開・照会・終了・close の失敗時にどのハンドルを誰が保持し、監視プロセスまで停止した場合に誰が処理を識別・終了確認するかを決める必要がある。模擬 API の失敗戻り値と実際の OS 失敗は区別する。API や監視自体が停滞する場合の無条件の期限・終了保証は成立したと扱えない。現行 `plan-02.md` の「保証できない場合は実行を止める」は維持される。
3. **承諾範囲と不明時の扱いを保持する。** `live-plan-02.md` は指定された公開リポジトリ・固定マーカーの新規 Issue 1件と指定ラベルに限定したユーザーの書込み承諾を記録し、既存 Issue / PR の変更を除外する。その資料に記載された範囲を超える承諾は推定しない。承諾が検証用 Issue の書込みを対象とすることと、現行計画の終了保証条件を満たすことは別の確認事項である。新たな承認を求めるべきかは案だけから断定しない。結果不明では POST を再送せず、前回の計画どおり以後の書込みを停止し、実行中でないことと全ページのマーカー・番号・実状態を確認して記録する。監視・プロセスの状態を識別できない場合は確認不能として保留する。
4. **秘密と復旧手順が設計段階。** トークンは実行時にメモリー・子環境に現れるため、生出力・コマンドライン・記録への露出を避ける従来条件を引き継ぐ。監視側のログと失敗経路も同じ保護が必要。監視が応答しないときの対象版・PID/ハンドル・生存・結果不明の確認方法、ユーザーに安全に引き渡す記録、重複 POST を防ぐ一回限りの証拠は具体的な実装・試験が未了。

## 次の合成検証

対象とハッシュを固定し、偽資格情報・ローカル合成データのみで、単一プロセスに必要な通常処理、子作成拒否、保持・非保持子孫、登録・再開・照会・終了・close の各失敗、監視消失や期限超過、ログへの秘密混入を検証する。終了確認は起動時から保持した対象ハンドル等で行い、識別不能・close の実際の失敗・同期 OS 停滞は未保証として残す。これらにより合成環境の挙動は調べられても、OS の無応答を無条件に排除する証明にはならない。実 GitHub・Credential Manager・製品 UI は今回確認していない。
