# 実 GitHub 検証の実行方式案 03（未承認）

## 目的と現状

ユーザーが承諾した公開リポジトリのテスト Issue 一件の作成・全列移動・最終 close を、製品と同じ Rust 処理で確認する。承認済み `../20261120-current-review/live-plan-02.md` の対象・ラベル・マーカー照合・一度限りの POST・各ステップの確認・秘密保護を維持する。前回の実行方式は `harness-review-02.md` で全体期限と OS 障害時の子孫停止が未証明。実行は無効のままである。

## 代替方式の検討案

- 対象の Rust テストと `gh auth token` の子孫を必要としないことを対象版のコードと実行時観測で確認し、それぞれの Job に ActiveProcessLimit=1 を設定して子孫の起動を拒否する。Job への設定と suspended 作成・登録が成功しない場合は再開しない。想定外の子作成を阻止できない環境なら停止する。
- 外側の監視プロセスが各子のプロセスハンドルを保持し、段階ごとに期限を設ける。期限切れ・異常時は Job 終了を要求し、親子のプロセス終了を独立したハンドルで確認する。終了できない、結果を読み取れない、Job 操作が失敗した場合は成功とせず、後続の書込みを一切開始しない。Rust の HTTP クライアントは既に20秒の要求期限と再試行無効を使用しているが、テスト全体の制限とは区別する。
- 書込み中に停止・通信不明となった場合は、その Issue の最終状態が不明である。自動 POST 再送や後続更新をせず、元の検証 Issue のマーカー・番号を全ページまたは API で読戻し、まだ処理が実行中でないことを確認するまで再実行しない。
- API や OS 自体が応答しない・ハンドル操作が拒否される場合、外側の監視を含む同期 OS 呼出しの完了や停止をソフトウェアだけで無条件に保証できない。これは現計画 `plan-02.md` の「保証できない場合は実行を止める」と未解決の差がある。既存計画を変更したことにはせず、実行許可の根拠として使わない。

## 検討事項

1. ActiveProcessLimit=1 が現行テストの実際のプロセス構成に適合し、子生成の抑止を合成試験と独立観測で示せるか。
2. 親の終了検出と Job ハンドルの後片付けを、正常・timeout・登録・再開・照会・終了・close 失敗時にどこまで確認できるか。疑似失敗と実 OS 失敗を混同しない。
3. 監視プロセス自身の生成や同期 OS 呼出しが停止した場合の扱い、実行者が安全に確認できる具体的な復旧手順、再送禁止の根拠。
4. 以前のユーザー承認と現行計画に対し、この条件付き保証で実行することが認可済みか。解釈が不明なまま実行せず、独立レビューと必要な判断を先に記録する。

これは提案であり、テスト実行の許可、承認済み計画の変更、実 GitHub 書込みの開始を意味しない。
