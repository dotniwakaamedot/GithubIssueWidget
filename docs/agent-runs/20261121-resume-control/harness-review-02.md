# 合成試験変更の独立確認 02

判定: **試験変更と記録の対象版を確認。実 GitHub 実行の blocking は継続。** 作者 `/root` と確認者 `/root/harness_check` は別担当。今回の依頼は試験が示す範囲の照合であり、実行方式の安全性や実 GitHub 書込みを承認しない。

## 確認できたこと

- `harness-result-02.md` に記載の4ファイルとログの SHA256 は実体と一致した。管理側ログ `synthetic-test-restart-03.log` は10件 OK を示し、単独試験ログ2件もそれぞれ1件 OK を示す。終了コード0は管理の記録によるもので、unittest ログ自体には元プロセスの終了コードはない。今回、管理外の一時領域を用いる合成試験の独立再実行は行っていない。
- `watch_process` は PID ファイルを監視し、実行中と判定したプロセスハンドルを取得し、その同一ハンドルを終了後に最大3秒待機する。保持・非保持の子孫、query・terminate・close の模擬失敗でテストしている。今回のログはその対象版・観測条件で期待する判定が得られた証拠であり、以前の2件の `WAIT_TIMEOUT` の原因や、どの変更がその原因を解消したかは証明しない。PID ファイルと期待した子孫の同一性は OS ハンドルの取得以前には独立検証されていない。
- `CloseHandle(job)` の失敗戻り値は結果不明として扱う変更を静的に確認した。close の模擬は実際には `real_close(handle)` を呼んだ後に失敗を返すため、OS がハンドルを閉じられなかった状況や、その場合の子孫終了は検証していない。query・terminate も呼出し戻り値の模擬であり、実 OS 障害そのものではない。

## 残る blocking と未確認

1. **異常時の全子孫終了の保証は未達。** Job 終了・照会・ハンドル close が本当に失敗した場合、特に close が実際に失敗したとき、全子孫が終了したことを実装側が別の手段で確認できる証拠はない。エラーを結果不明とするだけでは生存中の書込みを止めた証明にならない。実行前に独立した監視・停止設計と異常系の検証を整えるか、無効のまま保つ。
2. **実行全体の期限は未達。** `Popen` と同期 Windows API 自体の上限は設けられておらず、親の報告どおり生成から終了回収までの期限は保証できない。Job 外への breakaway、既存 Job の制約と実 OS 失敗も未検証。対象版では `run-live.py` の無条件 return が維持され、実 GitHub の更新は有効化されていない。停止解除は別版として再検証・独立確認が必要。
