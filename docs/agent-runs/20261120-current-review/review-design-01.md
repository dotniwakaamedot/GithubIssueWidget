# 移動処理の設計レビュー

結論: **非ステータスラベルの全置換をやめ、指定ラベルだけを追加・削除すれば B1 の非ステータスラベル消失を避けられるが、複数操作は原子的にならない。** 外部のステータス変更や Open / Closed 変更との競合、途中失敗は別途扱う必要がある。GitHub API の条件付き更新の可否・各エンドポイントの詳細は本調査では未確認。

- 既存 `movement.rs:21-27` は GET 後に全ラベルを PATCH し、別利用者の途中追加を消し得る。対象外ラベルに触れない個別操作なら、その操作による対象外ラベルの置換は発生しない。ステータスラベルだけを事前に列挙し、対象外は削除しない。
- ラベル操作と state 操作の間には必ず中間状態ができ、順序だけでは解消できない。例えば Done への変更でラベルが更新された後にクローズが失敗する、Done からの変更で再オープン後にラベル更新が失敗する可能性がある。アプリの分類規則は Closed を優先するため、途中表示にも注意する。各段階で失敗・結果不明を成功と扱わず、再取得を促す。
- 旧ステータスを削除してから新ステータスを追加すると、一時的にステータスなしになる。先に追加すると一時的に複数存在する。どちらも他クライアントから見える可能性があり、既存の分類順序によって意図と異なる列に見える。書込み回数を抑え、選択した順序と中間状態を明記する。
- GET 時の `updated_at` 比較だけでは、その後の別利用者の変更を防げない。外部の状態変更は state PATCH で、外部の同一ステータスラベル変更は削除や追加で競合し得る。終了時の再取得は食い違いを検出できる場合があるが、その後の変更や、意図が一致して見える上書きは検出できない。未確認の条件付き書込みを保証として扱わない。
- 途中の HTTP 拒否、応答消失・タイムアウト、最終再取得失敗を区別する。既に成功した段階がある場合や結果不明の場合は部分適用の可能性を表示し、盲目的な自動再試行や既存値へのロールバックを避ける。再取得後も外部競合は防げない。
- 検証案: GET 後に非ステータスラベルを追加する決定的な模擬試験、各段階の拒否・応答消失・再取得失敗、競合するステータス・state 変更、6 方向の最終状態、外部ラベル保持を検査する。模擬試験と実 GitHub 操作の結果は分けて記録する。

このレビューはソースの読取りによる設計検討であり、実行試験・外部通信・コード変更は行っていない。今回の調査の失敗はなし。
