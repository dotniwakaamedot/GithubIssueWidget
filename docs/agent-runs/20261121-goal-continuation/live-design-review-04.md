## Blocking B01: クラッシュ時の予約・識別・復旧を実装できる粒度で固定していない

案は排他的予約・保存読戻し、停止状態の子生成、PID と生成時刻、Job 登録を要求する一方、予約と状態ファイルの所在・作成方法・耐久性・読戻し・排他単位、各操作の前後で監督者が死亡した場合の復旧表を未指定としている。特に子生成後、PID/生成時刻の永続化前に監督者が死亡したときは、後任がその子を識別できない可能性があり、安全な終了確認や再実行可否を決められない。現在の方針は不明時に中止するため、この欠落だけから実際に書込みが再開されるとは判断しない。

修正案: 固定された状態領域・原子的な排他作成と耐久化・読み戻しの具体方式、各変更の順序、監督者死亡時に既存 `reserved`/`started`/`running` をどう保守的に解釈するかを記述する。生成から Job 登録までの各境界、プロセス識別情報未保存、PID 再利用、所有者不明、Job ハンドルが閉じられない場合を表にし、確認不能は手動復旧を含め書込み禁止とする。合成試験に各境界での突然終了・再起動と予約の再利用禁止を含める。ハンドルと OS の障害に対する無条件の停止保証は主張しない。

## Blocking B02: 安全な出力・認証・成功判定の実装境界が未定

案は子環境とメモリーにトークンを限定し、出力を固定値に変換するが、認証プロセスの取得・失敗時・パイプが大量出力や子孫に保持される場合の上限と後片付け、成功に必要な固定イベントの順序・完全性、最終読戻しとの対応を具体化していない。偽トークンのテスト項目だけでは例外経路や生出力が外へ出ない設計を検証できない。対象の `gh auth token` のヘルパー構成も未確認で、`gh --version` の成功はその代用にならない。

修正案: 生の stdout/stderr・例外を記録しない境界、メモリー／ストリーム上限超過時の中断・生存確認、制限時の子孫と実際の認証構成の扱いを定める。`finished` に必要な１回の作成結果、各ステップ順序、終了コード、最後の実状態確認を表にし、欠落・重複・不明は成功扱いにしない。固定ダミー秘密を用いた例外・大量出力・保持パイプの合成試験を独立レビューする。
