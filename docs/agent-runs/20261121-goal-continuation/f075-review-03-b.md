元レビューは、対象版が100件未満で停止し `Link` の `rel=next` を調べず、実応答ヘッダーも保存されていないため、記録された０件は全ページ照合の証拠にならないと指摘した。実際に次ページがあったことも、照合結果が誤っていたことも未確認。現行ソースも `collect` の短いページでの return と JSON 本文のみを返す `fetch_page` を確認できるが、版が違うため上記レビューを現行版の合否として扱わない。

F-075 発生1・2は取得失敗の診断不足と配列の誤集計であり、3件目は終端判定の証拠不足。いずれも完全性を証明できない点と不明を成功扱いしない対策を共有するが、同じ内部原因と断定しない。F-064 は配列階層という発生2との共通点に限り関連し、発生3の原因との同一性は未確認。処理内の停止条件は失敗記録の累計と分けて判断する。

既存 `AGENTS.md` と教訓は配列・ページ結合の合成試験と取得完了の区別を求めるが、終端を何の証拠で決めるか、次ページが残る短いページを試験することまでは明示していない。行数だけでは、観測した応答から次ページがないことを証明できないという本レビューの指摘を満たせない。

## ルール追記案

> ページ付き外部一覧の完全性が必要な場合は、取得元の仕様に基づく終端の根拠を事前に決め、応答の次ページ情報と対象・順序を確認する。短いページ、空のページや成功終了コードだけで終端を決めない。ページ情報が欠落・不正、循環、上限到達、途中失敗、対象不一致なら完全取得や不存在と扱わない。合成試験には短いページに次ページがある場合、正常終端、途中失敗と不正・循環を含める。秘密や本文を記録せず、実行時の観測範囲と並行更新による限界を残す。

GitHub の対象では信頼できる応答の `Link` と `rel=next` を確認する設計を検討し、次リンクを使う場合は対象・経路を固定・検証する。外部への再取得は停止条件と実行計画を満たしてから行う。取得中や取得直後の更新でスナップショットが保証されない点は別の制約として残す。対策の効果と現行版の安全性は未検証。
