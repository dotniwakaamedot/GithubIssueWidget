# Issue 一覧確認の独立レビュー

判定: **要修正（blocking 1件）**。作者 `/root`、確認者 `/root/live_next`。今回の実 GitHub 再取得・書込み、テスト独立再実行は行っていない。計画の実書込み許可やアプリ完成の判定ではない。

## Blocking B01: 全ページ照合の根拠が不足

`issue-enumeration.py` の `collect` は100件未満のページを受け取ると終了する一方、`fetch_page` は `gh api` の JSON 本文のみ取得しており、`Link` の `rel=next` を確認していない。ページが短い場合に次ページがないことはこの応答・ログから独立に検証されていない。今回の実応答ヘッダーは保存されず、実際に次ページがあったという事実も確認していない。従って結果記録の「１ページ・一致０件」は親の実行記録として扱え、**承認済み計画で要求される全ページの完全照合や POST の開始根拠にはできない**。

修正案: ステータスとページネーション情報を安全に取得し、信頼できる `next` の有無と対象・ページ制約を検証する。短いページに `next` がある合成応答、不正・循環・失敗時に成功としないケースを追加する。後続のページで結果不明・未完了なら一致０を返さない。実際の一覧取得は再実行の権限・停止条件を満たし、外部書込みのための直前 preflight として別に検証する。取得中の concurrent update はスナップショット保証がなく、取得後の変更も除外できない。

## Non-blocking N01: 障害の種別が記録されない

`fetch_page` の `gh` 非０終了コードを含む例外も、`main` では固定の失敗文に統一される。秘密や非公開の本文・外部の生エラーを表示しない点は適切だが、timeout、CLI の非０終了、JSON/データ形式の違いが記録から区別できず、失敗記録・原因切り分けに必要な情報が不足する。固定の分類と安全に取得した数値終了コードのみを記録し、標準出力・標準エラー・例外メッセージ・トークンをそのまま保存しないことを推奨。分類が意図どおりで、生データが漏れない合成テストも追加する。これは問題の観測性の指摘であり実際に秘密が漏れたという事実はない。

## 条件と証拠の範囲

- `collect` はページ型、100件超、各 Issue の番号・タイトル・本文を検証し、完全ページの次ページを要求する。４件の合成テストログは正常系と一部不正入力で `OK` を示す。テストログ単体は元プロセス終了コードを含まず、終了コード0は親の記録による。
- テストは短いページの next、ページ取得エラー、最大ページ数、タイムアウト、JSON パース失敗と秘密非露出を直接検証していない。`fetch_page` は subprocess の標準出力・標準エラーをメモリーで受け、失敗表示は固定文。実行環境と子プロセスにどの資格情報が渡るか、権限や全子孫終了は今回確認していない。
- マーカーは取得した title/body に対する部分文字列照合で、結果の０件は実行者に見えた取得結果の範囲に限る。認証・権限、応答ヘッダー、同時変更、ログの完全性は別に確認する。実応答や秘密の取得を今回再実行していない。
